# 02 网络请求与鉴权闭环

本章覆盖：HTTP 请求封装、Token 注入、刷新机制、并发控制、错误规范化、与页面/业务代码的边界。

## 2.1 现状（仓库对齐）

- 统一入口：`shengyu-ui/shengyu-ui-admin-uniappx/utils/request.uts`
- 文件/业务 API：集中在 `shengyu-ui/shengyu-ui-admin-uniappx/api/*.uts`

## 2.2 规范（Principles）

- **单入口**：页面与业务层不得直接调用 `uni.request`。
- **强约束**：
  - Token 仅由 request 层注入（页面不得手工拼 `Authorization`）。
  - baseUrl 仅由 request 层决定（页面不得拼 `API_BASE_URL + '/xxx'`）。
- **错误可观测**：
  - request 层必须能输出关键上下文（url/method/code），但不得泄漏敏感信息。
- **可恢复**：
  - 401 触发刷新 Token 时，需要处理并发与队列，避免“风暴刷新”。

## 2.3 模板/封装落点（Where & How）

### 2.3.1 request 封装职责清单

request 层应承担：

- header 规范化（避免大小写重复）
- tenant-id 注入（如开启租户）
- GET 禁用缓存
- JSON 解析与响应结构归一
- 401 自动刷新与请求队列重放
- 错误码转换为统一错误对象（建议）

### 2.3.2 API 文件职责清单

`api/*.uts` 应承担：

- 仅做 endpoint 封装与参数拼接
- 返回强类型（type）
- 不处理 UI toast

页面应承担：

- loading 状态
- toast/弹窗
- 业务流程编排

## 2.4 Reviewer Checklist

- 禁止项：
  - 页面/组件直接调用 `uni.request`
  - 页面拼 `API_BASE_URL + '/xxx'`
  - 页面手工设置 `Authorization`
- 必须项：
  - 新增接口必须进入 `api/*.uts`
  - 新增需要鉴权接口必须走 request 封装

## 2.5 常见问题（Troubleshooting）

- **JSON.parse 失败**：检查后端是否返回了非 JSON（例如 HTML 错误页）。
- **401 循环**：检查刷新 token 接口是否被加入白名单；检查 refresh-token 返回结构是否符合预期。
