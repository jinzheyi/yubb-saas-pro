# 扩展功能任务文档

## 1. 文档目的

本文档用于沉淀 `shengyu-ui/shengyu-ui-admin-uniappx` 的扩展功能任务说明。当前先纳入“切换主题”与“设置 -> 聊天气泡”两项能力，后续还会继续追加其它功能模块。

目标是基于当前项目真实代码结构，把每项扩展能力拆成可执行、可排期、可验收的任务说明，避免一次性改造过大导致返工。

本文档聚焦：

- 前端 uni-app x / uni-app 页面主题体系建设
- 聊天气泡个性化配置体系建设
- 用户主题偏好的本地持久化与多端同步
- 用户聊天气泡偏好的本地持久化与多端同步
- 后端用户资料扩展以支持主题偏好同步
- 后端用户偏好扩展以支持聊天气泡同步
- 渐进式替换现有硬编码颜色，避免大范围回归
- 形成统一的扩展功能任务编写模板，便于后续继续追加

## 1.1 文档使用原则

本文档是“扩展功能总任务文档”，不是单一功能设计文档。

使用原则如下：

- 每个功能模块可独立追加，不要求必须与其它功能并行开发
- 每个功能模块应独立包含
  - 现状调研
  - 目标定义
  - 分阶段任务
  - 风险
  - 验收标准
- 是否并行开发、串行开发，取决于实际排期和优先级，不由本文档强制规定
- 当多个功能存在依赖关系时，只说明“建议顺序”与“依赖关系”，不强行要求同一阶段一起开工

## 2. 当前现状调研结论

### 2.1 已存在的基础条件

当前仓库中已经具备一些可复用基础：

- 个人页存在“切换主题”入口，但目前仅是 UI 入口，没有真实逻辑
  - `shengyu-ui/shengyu-ui-admin-uniappx/pages/profile/profile.uvue`
- 前端已有本地存储模式，可直接复用
  - `store/user.uts`
  - `store/locale.uts`
- 当前用户资料获取链路已存在，适合作为后续“主题偏好同步”的基础
  - 前端：`api/user.uts` 中 `getCurrentUserDetail()`
  - 后端：`/system/user/get-profile`
- 项目已有设置页入口，可以承接后续主题设置页
  - `pages/profile/settings.uvue`
- 当前国际化文案已有“切换主题”字段
  - `locales/zh-CN.uts`
  - `locales/en.uts`
- 设置页已经存在“聊天气泡”入口
  - `shengyu-ui/shengyu-ui-admin-uniappx/pages/profile/settings.uvue`
- 已存在聊天气泡设置页原型
  - `shengyu-ui/shengyu-ui-admin-uniappx/pages/message/chat-bubble.uvue`

### 2.2 当前问题

当前项目并不具备真正的主题体系，具体表现为：

- 没有全局主题状态管理
- 没有主题服务或主题 store
- 没有统一的主题 token 定义
- 绝大多数页面颜色直接硬编码在各 `.uvue` 文件中
- 没有“跟随系统 / 浅色 / 深色”模式定义
- 没有后端用户主题偏好字段
- 没有登录后恢复服务端主题配置的链路

当前“聊天气泡”能力也只是原型页面，具体表现为：

- `chat-bubble.uvue` 仅能本页预览，未真正接入聊天页渲染
- 颜色保存逻辑仍是注释状态，没有真实本地持久化
- 聊天页 `pages/message/chat.uvue` 的自发消息气泡仍使用固定样式
- 没有“气泡配置 store / service”
- 没有后端气泡偏好字段
- 没有和主题体系的边界约束
  - 主题负责全局视觉基线
  - 气泡负责消息发送方气泡的个性化颜色/样式

### 2.3 风险判断

如果现在直接做“全局深色模式一键切换”，风险很高：

- 大量页面会出现颜色不统一
- 某些页面会出现浅底深字和深底深字混用
- TabBar、导航栏、状态栏、弹层、输入框等跨端表现可能不一致
- 安卓、iOS、H5 的表现差异会放大

因此不建议一步到位，应采用“先建体系，再逐步接入页面”的渐进方案。

### 2.4 uni-app 官方能力边界补充

结合 uni-app 官方文档，“切换主题”在安卓、iOS、H5 是具备官方底层支持的，但需要明确区分“官方 darkmode 底座”和“业务层主题能力”。

#### 2.4.1 官方已经支持的底层能力

- `App` 与 `H5` 支持 darkmode 配置
- 可通过 `manifest.json` 开启暗黑模式支持
- 可通过 `theme.json` 定义 `light / dark` 两套主题变量
- 可在 `pages.json` 中通过 `@变量名` 引用主题变量
- 可通过 `uni.onThemeChange` 监听系统主题变化
- 可通过 `uni.setNavigationBarColor` 动态设置导航栏颜色
- 可通过 `uni.setTabBarStyle` 动态设置 tabBar 样式

#### 2.4.2 官方能力无法直接替代完整业务功能

官方 darkmode 更偏向解决：

- 跟随系统主题
- 原生导航栏 / tabBar / pages.json 配置适配
- 系统主题变化监听

但它不能直接替代以下业务能力：

- 用户手动选择 `light / dark / system`
- 用户主题偏好的本地存储
- 登录后恢复用户主题偏好
- 页面内容层 token 管理
- 主题与聊天气泡等个性化视觉能力协同

结论：

- `manifest.json + theme.json + pages.json` 是主题底座
- `store/theme.uts + token + 页面消费` 是完整主题能力主体

#### 2.4.3 官方兼容性与前置条件

根据官方文档，需要在设计说明中明确以下前提：

- 暗黑模式能力依赖 `HBuilderX 3.6.9+`
- `uni.onThemeChange` 支持范围
  - App：`iOS 2.6.5+`、`Android 3.6.9+`
  - H5：`HBuilderX 3.6.9+`
- 设备系统侧要求
  - `iOS 13+`
  - `Android 10+`
- App 端若未开启 `darkmode:true`，`uni.getSystemInfoSync()` 返回值中不会带 `theme`

#### 2.4.4 开工前必须补齐的基础配置说明

“切换主题”正式开工前，文档中必须明确这些前置项：

1. `manifest.json`
   - `app-plus.darkmode = true`
   - `h5.darkmode = true`
   - `themeLocation = "theme.json"`
2. `theme.json`
   - 定义 `light / dark` 变量
3. `pages.json`
   - 导航栏、背景、tabBar 优先通过 `@变量` 引用
4. 页面内容层
   - 仍然由业务 token 控制，不直接依赖 `pages.json`

#### 2.4.5 多端专项坑位

需要在设计说明中显式记录这些坑位：

- iOS 安全区暗色适配
  - 需关注 `manifest.json -> app-plus -> safearea -> backgroundDark`
- Android 导航栏颜色限制
  - 官方说明 `setNavigationBarColor` 在 Android 上对纯黑、纯白取值有限制
- 导航栏动态设置时机
  - 官方建议 `onReady` 调用，避免被框架覆盖
- H5 自定义 tabBar
  - 官方 `custom-tab-bar` 仅 H5 支持，不能默认认为 App 可共用

#### 2.4.6 对当前设计文档的直接影响

因此“切换主题”模块必须补充这些实施约束：

- 第一阶段不只是做 `theme store`
- 第一阶段必须同时落地 darkmode 底座配置
- `system` 模式依赖官方能力
- `light / dark` 手动模式由业务层覆盖
- 原生层与页面内容层必须分层设计
  - 原生层：`theme.json / pages.json / navigationBar / tabBar`
  - 页面层：业务 token、运行时样式、组件颜色

## 3. 当前已纳入的功能模块

当前文档已纳入以下扩展能力：

1. 切换主题
2. 设置 -> 聊天气泡

后续可继续追加的典型模块包括但不限于：

- 聊天背景
- 消息列表个性化
- 会话视觉增强
- 用户偏好同步类能力
- 其它设置中心扩展项

## 4. 总体设计目标

视觉个性化能力建设目标如下：

1. 支持三种主题模式
   - `light` 浅色
   - `dark` 深色
   - `system` 跟随系统
2. 支持聊天气泡个性化配置
   - 预设颜色
   - 自定义颜色
   - 后续可扩展样式
3. 支持本地持久化
4. 支持登录后恢复配置
5. 支持后续多端同步
6. 优先改造核心页面，逐步覆盖全站
7. 兼容安卓、iOS、H5
8. 不影响现有登录、消息、联系人、个人中心等核心链路

## 5.1 功能模块 A：切换主题

### 5.1.0 模块说明

本模块描述“切换主题”的任务设计。

说明：

- 本模块可独立排期实施
- 可先做，也可根据优先级晚于其它扩展功能
- 若后续存在与其它视觉能力的复用关系，应复用底层能力，不要求业务层并行推进

### 5.1.1 第一阶段：前端本地主题偏好能力

### 5.1.1.1 阶段目标

先把“主题功能真正跑起来”，但只做前端本地能力，不依赖后端。

这一阶段完成后，用户已经可以：

- 在设置页选择浅色 / 深色 / 跟随系统
- 退出重进后保留主题偏好
- 在若干核心页面看到主题切换效果

### 5.1.1.2 设计原则

- 不直接全站改造
- 先建立统一主题状态和 token
- 优先改造核心高频页面
- 允许旧页面暂时继续使用硬编码颜色
- 必须区分“官方 darkmode 底座”和“业务层主题状态”
- `system` 模式优先依赖官方 darkmode 能力

### 5.1.1.3 前端改造任务

#### 任务 A：新增主题 store / service

建议新增：

- `shengyu-ui/shengyu-ui-admin-uniappx/store/theme.uts`
  或
- `shengyu-ui/shengyu-ui-admin-uniappx/services/theme-service.uts`

建议能力包括：

- `getThemeMode(): 'light' | 'dark' | 'system'`
- `setThemeMode(mode)`
- `resolveActiveTheme()` 解析当前实际主题
- `initTheme()` 应用本地主题
- `subscribeThemeChange(listener)` 页面监听主题变化

建议存储 key：

- `APP_THEME_MODE`

建议实现方式：

- 使用 `uni.getStorageSync / uni.setStorageSync`
- `system` 模式下结合 `uni.getSystemInfoSync()` 获取当前系统外观
- 在 H5 / App 统一维护一份主题状态
- 监听 `uni.onThemeChange`
- 当模式为 `system` 时，系统主题变化要自动刷新
- 当模式为 `light / dark` 时，系统变化不应覆盖用户手动选择

#### 任务 A-1：补齐官方 darkmode 底座配置

该任务属于主题功能的正式前置项，不应遗漏。

建议改造：

- `manifest.json`
  - `app-plus.darkmode = true`
  - `h5.darkmode = true`
  - `themeLocation = "theme.json"`
- 新增或完善项目根级 `theme.json`
- `pages.json`
  - `navigationBarBackgroundColor`
  - `navigationBarTextStyle`
  - `backgroundColor`
  - `backgroundTextStyle`
  - `tabBar.color`
  - `tabBar.selectedColor`
  - `tabBar.backgroundColor`
  - `tabBar.borderStyle`
  尽量优先改成 `@变量` 引用

说明：

- 如果跳过该任务，`system` 模式会天然不完整
- 页面内容层依旧需要业务 token，但原生层优先走官方方案

#### 任务 B：新增主题 token 定义

建议新增：

- `shengyu-ui/shengyu-ui-admin-uniappx/config/theme.uts`

内容建议包括：

- 基础语义色
  - 页面背景
  - 卡片背景
  - 一级文字
  - 二级文字
  - 分割线
  - 品牌主色
  - 危险色
  - 输入框背景
  - 气泡背景
- 两套 token
  - `lightThemeTokens`
  - `darkThemeTokens`

示例语义不要直接绑定页面名，应绑定“用途”：

- `pageBg`
- `cardBg`
- `textPrimary`
- `textSecondary`
- `borderColor`
- `brandPrimary`
- `navBg`
- `navText`
- `inputBg`
- `tabBarBg`

补充要求：

- token 不要直接等同于 `theme.json` 变量
- `theme.json` 负责原生层
- 业务 token 负责页面内容层
- 两者允许映射，但不要耦合成一套不可维护结构

#### 任务 C：新增主题设置页

建议新增页面：

- `shengyu-ui/shengyu-ui-admin-uniappx/pages/profile/theme-settings.uvue`

页面功能：

- 选项
  - 浅色
  - 深色
  - 跟随系统
- 显示当前生效状态
- 修改后立即生效
- 返回个人页和设置页时状态保持一致

当前个人页 `profile.uvue` 的“切换主题”入口建议跳转到该页面，而不是直接 ActionSheet 立即切换。原因：

- 交互更清晰
- 后续能扩展主题预览、强调色、聊天背景等能力
- 可承接未来更多个性化设置

#### 任务 D：主题应用层

建议新增一个统一 helper，例如：

- `useTheme.uts`
  或
- `utils/theme.uts`

让页面通过统一方法取当前 token，而不是每页各自拼装逻辑。

例如页面内使用：

- `const theme = useTheme()`
- `theme.pageBg`
- `theme.textPrimary`

补充要求：

- 页面内容层尽量不要直接零散调用 `uni.setNavigationBarColor`
- 导航栏 / tabBar 等原生层变更应由主题服务集中管理
- 避免各页面各自处理导致切换时机不一致

#### 任务 E：优先接入核心页面

第一阶段不要全量改造，建议先接入以下页面：

1. `pages/profile/profile.uvue`
2. `pages/profile/settings.uvue`
3. `pages/message/message.uvue`
4. `pages/message/chat.uvue`
5. `pages/contacts/contacts.uvue`
6. `pages.json / manifest.json / theme.json`

优先原因：

- 用户感知最强
- 使用频率最高
- 颜色结构最典型
- 后续可沉淀可复用 token 经验

### 5.1.1.4 第一阶段验收标准

- 可切换 `light / dark / system`
- 主题模式本地持久化有效
- 核心页面主题切换后无明显文字不可见问题
- 安卓、iOS、H5 三端基础样式正常
- 不要求全站统一，但核心页面必须统一
- `system` 模式可正确响应系统主题变化
- 原生导航栏和 tabBar 与页面主题不割裂
- `uni.getSystemInfoSync().theme` 在目标端可稳定获取

## 5.2 功能模块 B：设置 -> 聊天气泡

### 5.2.0 模块说明

本模块描述“设置 -> 聊天气泡”的任务设计。

说明：

- 本模块可独立排期实施
- 不要求必须与“切换主题”并行开发
- 若先做聊天气泡，也只需复用必要底层能力
- 若后做聊天气泡，则应尽量复用已经沉淀好的主题 token / 通用视觉 helper

### 5.2.1 第一阶段：前端本地聊天气泡能力

### 5.2.1.1 阶段目标

先把“聊天气泡”从预览页原型做成真正可生效的能力，但同样先只做前端本地能力，不依赖后端。

这一阶段完成后，用户已经可以：

- 在 `设置 -> 聊天气泡` 选择预设颜色或自定义颜色
- 保存后立即在聊天页看到自己发送消息的气泡变化
- 退出重进后保留聊天气泡设置

### 5.2.1.2 设计原则

- 聊天气泡与主题能力解耦
- 主题决定页面整体明暗和语义色
- 聊天气泡只决定“自己发送消息”的气泡视觉
- 先做颜色配置，不先做复杂皮肤和图片背景

### 5.2.1.3 前端改造任务

#### 任务 A：新增聊天气泡 store / service

建议新增：

- `shengyu-ui/shengyu-ui-admin-uniappx/store/chat-bubble.uts`
  或
- `shengyu-ui/shengyu-ui-admin-uniappx/services/chat-bubble-service.uts`

建议能力包括：

- `getBubbleConfig()`
- `setBubbleColor(color)`
- `resetBubbleConfig()`
- `validateBubbleColor(color)`
- `subscribeBubbleChange(listener)`

建议本地存储 key：

- `APP_CHAT_BUBBLE_CONFIG`

建议配置结构：

```ts
type ChatBubbleConfig = {
  color: string
  mode: 'preset' | 'custom'
}
```

#### 任务 B：完善聊天气泡设置页

目标文件：

- `shengyu-ui/shengyu-ui-admin-uniappx/pages/message/chat-bubble.uvue`

需要补齐：

- 页面初始化时读取本地配置
- 点击“确定”后真实写入本地存储
- “恢复默认”恢复默认气泡色
- 自定义颜色增加格式校验和容错
- 预览区文本颜色算法修正

当前 `getTextColor()` 返回值实际没有区分浅深背景，后续需要按亮度算法计算，以保证深浅背景文字可读。

#### 任务 B-1：明确聊天气泡第一阶段作用范围

为了防止实现过程中范围失控，第一阶段必须明确只改这些场景：

- 我发送的文本消息气泡
- 我发送的引用消息气泡
- 我发送的语音消息气泡
- 我发送的合并转发消息气泡

第一阶段明确不改：

- 图片消息
- 视频消息
- emoji 表情
- 自定义收藏表情
- 纯透明或无气泡类型消息

以下类型建议放到第二阶段评估：

- 文件消息
- 位置消息
- 名片消息
- 其它卡片型消息

说明：

- 如果第一阶段不先把范围写死，开发时容易把“聊天气泡”误做成“所有消息样式全量改造”
- 这会显著放大回归风险和联调成本

#### 任务 B-2：补齐聊天气泡颜色派生规则

聊天气泡配置不应只等于一个基础背景色。

真实聊天页还涉及多种相关颜色状态，建议统一定义为 `bubble tokens`，由一个基础色派生出一组运行时颜色，而不是在聊天页散落硬编码。

建议至少包含：

- `selfBubbleBg`
- `selfBubbleText`
- `selfBubbleBorder`
- `selfBubbleVoicePlayingBg`
- `selfBubbleVoicePausedBg`
- `selfBubbleWaveColor`
- `selfBubbleProgressColor`
- `selfBubbleSubText`

设计约束：

- 后端只保存基础配置
- 派生色由前端 helper 统一计算
- 不允许在 `chat.uvue` 里继续散落写死一组“自发消息专用蓝色变体”

#### 任务 B-3：补齐文字对比度与颜色合法性规则

当前原型页文本颜色算法不足，正式设计中必须补充这些要求：

- 自定义颜色保存前必须经过合法性校验
- 必须根据背景色亮度自动计算推荐文字色
- 必须保证文本可读性
- 若颜色与文字对比度不达标，应：
  - 拒绝保存
  或
  - 自动纠偏到安全文字色

建议验收要求：

- 浅色背景下正文、次级文字都可读
- 深色背景下正文、次级文字都可读
- 语音状态、进度条、波形等状态色不能因为基础色变化而失真

#### 任务 B-4：补齐设置后实时刷新机制

文档应明确规定：

- 用户在 `聊天气泡` 设置页点击“确定”后
- 当前已打开的聊天页应实时刷新
- 不应要求用户退出并重新进入聊天页才能看到效果

建议实现约束：

- 气泡 store / service 需要支持订阅通知
- `pages/message/chat.uvue` 需要监听气泡配置变化
- 设置成功后应立即触发当前会话 UI 刷新

#### 任务 B-5：补齐默认值、回退值与迁移策略

当前默认气泡色应在文档里明确写死，而不是散落在页面样式里。

建议第一阶段默认值：

- 默认基础气泡色：`#D2E3FC`
- 默认模式：`preset`

并补齐这些回退策略：

- 本地没有配置时，回退默认值
- 本地配置非法时，回退默认值
- 服务端字段为空时，保留本地值或默认值
- 老用户升级后，没有历史配置时，自动初始化默认值

#### 任务 B-6：补齐预览与真实聊天页一致性要求

聊天气泡设置页不能只保留一个过度简化的预览。

建议明确要求：

- 预览区尽量复用真实聊天页的气泡 token
- 至少展示：
  - 文本消息预览
  - 语音消息预览
  - 合并转发消息预览
- 预览结构与真实聊天页风格保持一致

这样可以避免：

- 设置页看起来很好
- 真实聊天页效果完全不同

#### 任务 B-7：补齐后端字段边界说明

第二阶段服务端同步时，建议明确字段边界：

- 服务端先只保存基础配置
  - `chatBubbleColor`
  - `chatBubbleMode`
- 不保存前端派生色
- 不保存运行时状态色
- 派生 token 始终由前端计算

这样可以避免后端字段过早膨胀，也避免后续换算法时服务端数据不兼容。

#### 任务 B-8：补齐与主题能力的优先级关系

虽然聊天气泡与主题能力解耦，但仍需明确优先级关系：

- 主题负责页面整体背景、文字、输入框、导航栏、tabBar
- 聊天气泡只覆盖“自己发送消息”的气泡视觉
- 切换主题后，聊天气泡配置仍然保留
- 但聊天气泡的文字色、状态色、派生色应重新计算，以适配当前主题环境

这条规则写清楚后，后续实现时才不会出现：

- 深色主题下仍沿用浅色主题的派生文字色
- 聊天气泡和页面整体视觉割裂

#### 任务 C：接入聊天页真实渲染

目标文件：

- `shengyu-ui/shengyu-ui-admin-uniappx/pages/message/chat.uvue`

当前聊天页有大量固定气泡样式：

- `.message-self .bubble-text`
- `.message-self .bubble-voice`
- `.message-self .bubble-forward-combine`

第一阶段建议优先接入：

1. 文字消息气泡
2. 引用消息气泡
3. 语音消息气泡
4. 转发合并消息气泡

图片、视频、表情这类非标准文本气泡可放后续阶段。

建议实现方式：

- 当前用户发送消息气泡背景色从 store 读取
- 同步计算对应文字色
- 对所有“自发消息气泡”统一走同一套 helper
- 气泡配置变化后，当前打开的聊天页应立即响应刷新

#### 任务 D：新增气泡视觉 helper

建议新增：

- `utils/chat-bubble.uts`

建议内容：

- 默认气泡色
- 预设颜色列表
- 颜色校验函数
- 根据背景色计算文字色函数
- 根据配置生成样式对象函数

### 5.2.1.4 第一阶段验收标准

- 设置页修改后，聊天页自己的气泡立即生效
- 退出应用重新进入后配置仍保留
- 文本在浅色/深色气泡上均可读
- 安卓、iOS、H5 预览与真实聊天页表现基本一致
- 第一阶段作用范围严格受控，不扩散到未纳入的消息类型
- 气泡预览与真实聊天页关键样式保持一致

## 5.3 跨模块阶段：服务端偏好同步

### 5.3.1 阶段目标

在第一阶段稳定后，扩展为“登录账号级”的主题偏好同步。

这一阶段完成后，用户在一个端修改主题或聊天气泡，其他端登录后可恢复同样配置。

### 5.3.2 为什么第二阶段再做

因为当前项目还没有主题体系，如果先加后端字段，前端仍然无法稳定消费，会导致：

- 字段先上线但无收益
- 前后端联调成本提前发生
- 主题 token 未稳定前，服务端字段含义也不稳定

所以应在第一阶段稳定后再做服务端同步。

### 5.3.3 后端改造建议

基于当前已有用户 profile 链路，建议扩展用户资料字段：

候选字段：

- `themeMode`
- `chatBubbleColor`
- `chatBubbleMode`

候选值：

- `light`
- `dark`
- `system`

建议改造范围：

- 用户 DO / VO / Convert
- `get-profile` 返回值
- 新增“更新主题 / 聊天气泡偏好”接口

建议接口：

- `PUT /app-api/system/user/theme`
- `PUT /app-api/system/user/chat-bubble`

请求参数建议：

```json
{
  "themeMode": "dark"
}
```

也可考虑合并到现有用户偏好更新接口，但就当前项目状态，单独接口更清晰、风险更低。

### 5.3.4 前端联动改造

前端在登录后或进入 App 初始化时：

1. 先读取本地主题缓存
2. 拉取当前用户 profile
3. 若服务端有 `themeMode`，则覆盖本地
4. 应用主题与聊天气泡配置

这里补充实现约束：

- 登录恢复服务端主题前，不应阻塞首屏
- 可先用本地缓存快速应用，再异步用服务端值纠正
- 若服务端值为空，则保留本地值或默认值
- `system` 模式下，最终明暗效果仍以本机系统主题为准

用户在设置页修改主题时：

1. 先本地切换，保证即时反馈
2. 再异步请求服务端保存
3. 若服务端失败，不回滚 UI，但给出轻提示并保留重试策略

用户在“聊天气泡”页修改配置时：

1. 先本地切换并通知聊天页
2. 再异步请求服务端保存
3. 若服务端失败，不阻塞当前设置生效

### 5.3.5 第二阶段验收标准

- 服务端可存储并返回主题偏好
- 服务端可存储并返回聊天气泡偏好
- 多端登录可恢复相同主题与聊天气泡设置
- 本地即时切换不依赖接口返回
- 接口失败不会影响当前会话可用性

## 9. 风险与规避建议

### 8.1 风险：硬编码颜色过多

规避：

- 分批改造
- 先核心页面
- 新改代码强制用 token

### 8.1A 风险：只做业务层 store，漏掉官方 darkmode 底座

规避：

- 第一阶段把 `manifest.json / theme.json / pages.json` 纳入必做项
- 在开发任务中单列“官方 darkmode 底座配置”
- 单独验证 `system` 模式链路是否完整

### 8.2 风险：深色模式文字不可读

规避：

- 优先整理语义色
- 每改完一页做对比校验
- 不要直接反色

### 8.3 风险：三端表现不一致

规避：

- 安卓、iOS、H5 分别验证
- 系统栏与原生控件放到后续阶段独立处理

### 8.3A 风险：系统模式与手动模式互相覆盖

规避：

- 明确优先级
  - `light / dark` 手动模式优先级高于系统变化
  - `system` 模式才响应 `uni.onThemeChange`
- 统一在主题服务内部做模式判断

### 8.4 风险：后端字段上线后前端未消费

规避：

- 严格第二阶段再做后端同步
- 先把前端本地能力做稳定

### 8.5 风险：聊天气泡预览和真实聊天页不一致

规避：

- 设置页预览样式尽量复用聊天页真实气泡 token
- 文字色计算逻辑统一走 helper
- 先接入文本气泡，再扩展其它消息类型

## 12. 最终结论

当前项目适合采用“按功能模块独立规划、按公共能力复用、按优先级实施”的扩展方案。

对于当前已纳入的两项能力，推荐方向仍然是：

- 先建立前端本地能力
- 再做服务端同步
- 再做全站统一与增强能力

最关键的判断是：

- 第一阶段必须先做
- 聊天气泡与主题逻辑应保持解耦
- 第二阶段不要提前做
- 第三阶段要按页面批次推进
- 第四、五阶段属于增强与完善，不应阻塞前两阶段上线

按此方案推进，可以在不大规模重构现有代码的前提下，把多个扩展能力逐步纳入统一任务体系中，并保持文档可持续追加、可持续执行。
