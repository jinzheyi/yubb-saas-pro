# 群单聊设置页面设计任务文档

## 最终设计决议

- 群聊设置页与单聊设置页的消息设置统一为两个开关：
  - `消息免打扰`
  - `置顶聊天`
- 这两个开关必须接入现有会话主链路，不允许只做页面本地态：
  - 前端统一走 `conversationService`
  - 后端统一走 `PUT /system/im/conversation/update`
  - 多端一致统一依赖 `GET /system/im/conversation/sync`
- 群聊设置页保留两个核心入口：
  - `群文件`
  - `聊天记录`
- 单聊设置页保留两个核心入口：
  - `文件`
  - `聊天记录`
- 群聊的 `群文件` 与单聊的 `文件` 只是入口叫法不同，打开后统一进入同一个文件总览页。
- 统一文件总览页复用 `shengyu-ui/shengyu-ui-admin-uniappx/pages/message/chat-files.uvue`，页面内统一提供四个 tab：
  - `全部`
  - `图片`
  - `视频`
  - `文件`
- 统一文件总览页的数据口径按会话维度处理：
  - 单聊按当前 `chatId` 查询当前会话中的图片、视频、文件消息
  - 群聊按当前 `chatId` 查询当前群会话中的图片、视频、文件消息
- 页面标题按入口场景动态展示：
  - 群聊入口显示 `群文件`
  - 单聊入口显示 `文件`
- `聊天记录` 页统一复用 `shengyu-ui/shengyu-ui-admin-uniappx/pages/message/chat-history.uvue`
- 群聊设置页中的群管理项按企业 IM 真实价值分级处理：
  - `群聊邀请确认`：保留，属于群二维码 / 邀请链接加入链路的有效门槛控制，已接群组设置权威接口
  - `我在本群的昵称`：保留，属于企业群内身份识别核心能力，当前已补齐前后端主链路
  - `显示群成员昵称`：当前轮次不做，不建议继续保留为伪开关；若后续确有需求，应定义为端侧显示偏好，而不是群级业务设置

## 设计原则

- 会话设置必须服从单一状态源：
  - 会话列表页 `shengyu-ui/shengyu-ui-admin-uniappx/pages/message/message.uvue` 只消费 `conversationService` 的会话状态
  - 设置页修改成功后，也必须回到同一份会话状态，不能出现第二套状态源
- 微信 / 企业微信风格对齐原则：
  - `置顶聊天` 影响会话列表分组与排序
  - `消息免打扰` 不阻断消息接收，只影响提醒呈现与未读展示样式
  - 设置修改后当前端立即生效，且换端、重进、增量同步后不得回滚
- 入口命名遵循业务语义：
  - 群聊强调“群文件”
  - 单聊强调“文件”
- 打开后的页面交互尽量统一，减少用户学习成本与维护成本
- 文件总览页按会话消息维度展示，避免群聊、单聊逻辑分叉后出现功能不一致
- `im_group_file` 继续保留，作为群文件业务索引与后续企业微信式群文件管理能力的承载基础；但当前设置页打开的统一文件总览页不再依赖它作为唯一展示来源
- 群管理设置遵循企业 IM 的能力边界：
  - 会话级设置与群级设置必须分层，不能混用 `conversationService`
  - 群级设置优先保留“会影响加入门槛、群内身份识别、管理秩序”的能力
  - 纯展示偏好若没有稳定存储与明确消费位，不应伪装成已落地的业务设置

## 当前系统真实链路基线

### 1. 会话页状态源

- 会话列表页：`shengyu-ui/shengyu-ui-admin-uniappx/pages/message/message.uvue`
- 会话数据统一来自：`shengyu-ui/shengyu-ui-admin-uniappx/services/conversation-service.uts`
- UI 工作方式：
  - 首屏优先读 `conversationService.getConversations()` 当前内存态，快速渲染
  - 随后调用 `conversationService.loadConversations()` 做增量对齐
  - 页面回到前台时，先回显本地会话缓存，再按连接状态 / 最近同步时间 / 后台停留时长决定是否触发一次增量同步
  - `conversationService` 内部优先走 `GET /system/im/conversation/sync?cursorVersion=&limit=`
  - 服务层 merge 完成后，通过 `addUpdateListener` 通知消息页全量刷新
- 消息页表现规则：
  - `isPinned = true` 的会话进入置顶区并优先排序
  - `noDisturb = true` 的会话显示免打扰图标
  - `noDisturb = true` 且有未读时，显示红点而不是数字 badge

### 4. 群管理设置真实基线

- 群聊设置页：`shengyu-ui/shengyu-ui-admin-uniappx/pages/message/group-settings.uvue`
- 设计评审中重点讨论过三项群管理设置：
  - `群聊邀请确认`
  - `我在本群的昵称`
  - `显示群成员昵称`
- 三项能力现状并不一致，必须拆开判断，不可视作“都已支持”
- 当前代码实现中，页面实际保留的是前两项；`显示群成员昵称` 已从页面实施范围中移除，避免误导测试

#### 4.1 群聊邀请确认

- 业务价值判断：
  - 在企业微信式使用场景中有必要保留
  - 它影响的是“通过群二维码 / 邀请码 / 邀请链接加入时，是否需要管理员或群主审核”
  - 它不应影响群主 / 管理员主动拉人进群
  - 它也不应替代“是否允许普通成员邀请”的管理规则
- 与 `允许成员邀请` 的边界：
  - `群聊邀请确认`：控制“被邀请人自助扫码/邀请码入群”是否先进入审批
  - `允许成员邀请`：控制“普通成员是否有权主动把别人拉进群”
  - 群主/管理员主动拉人进群，不受 `群聊邀请确认` 影响
- 当前已具备：
  - 后端群实体 `ImGroupDO` 存在 `needApproval`
  - 后端群实体 `ImGroupDO` 同时存在 `allowMemberInvite`
  - `GET /system/im/group/get` 可读到 `needApproval`
  - `PUT /system/im/group/update` 已支持写入 `needApproval / allowMemberInvite`
  - 邀请码校验返回 `needApproval`
  - 加群页 `join-group.uvue` 已按 `needApproval` 展示“需要群主或管理员审核”的文案
  - 邀请码入群接口已改为返回结果态：
    - `1-直接入群`
    - `2-已提交申请`
  - 已新增加群申请单表：
    - `im_group_join_request`
  - 已新增管理员处理接口：
    - `GET /system/im/group/join-request/list`
    - `GET /system/im/group/join-request/pending-count`
    - `PUT /system/im/group/join-request/approve`
    - `PUT /system/im/group/join-request/reject`
  - 前端已新增管理员审批页：
    - `shengyu-ui/shengyu-ui-admin-uniappx/pages/message/group-join-requests.uvue`
- 当前缺口：
  - 当前版本已完成“申请提交 -> 管理员审批 -> 通过后入群”主链路
  - 当前已补充管理员实时通知、申请人结果通知
  - 尚未补充审批历史运营能力
- 结论：
  - 这是“群设置写链路 + 申请单 + 管理员审批页 + 通过后真正入群”均已打通的能力
  - 当前后续重点转为审批历史运营能力与通知中心展示完善，而不是主流程可用性

#### 4.1.1 允许成员邀请

- 业务价值判断：
  - 在企业 IM 中有必要和 `群聊邀请确认` 拆开
  - 它解决的是“普通成员能不能直接拉人”这一群治理问题
- 当前已具备：
  - 后端 `ImGroupServiceImpl#addGroupMembers` 已按规则校验：
    - 群主/管理员可直接添加
    - 普通成员仅在 `allowMemberInvite=true` 时可添加
  - 当前已补齐群设置页真实开关
  - 当前已补齐成员区 `添加` 按钮显隐与加人页准入校验
- 结论：
  - 这项能力现在和 `群聊邀请确认` 已完成职责拆分
  - 后续人工测试必须分别验证两条链路，不能再混为一个开关理解

#### 4.2 我在本群的昵称

- 业务价值判断：
  - 在企业 IM 中有必要优先实现
  - 对跨部门协作群、项目群、外包协作群尤为重要，可降低“同名员工 / 真实姓名不可辨识 / 角色不清晰”的沟通成本
  - 与 @ 提及、聊天记录识别、群成员列表显示都有直接关联
- 当前已具备：
  - 群成员数据对象 `ImGroupUserDO` 存在 `nickname`
  - 群成员列表接口已返回 `nickname`
  - 群设置页能从成员列表回填当前用户的 `myNickname`
  - 后端 service 已实现 `ImGroupServiceImpl#setMemberNickname`
  - service 语义支持“`memberUserId = null` 时设置自己的群昵称”，也支持群主设置他人昵称
- 当前缺口：
  - 若后续需要支持群主代改他人群昵称，还需补后台入口或成员管理页入口
- 结论：
  - 当前已补齐 `AppImGroupController -> api/group.uts -> group-settings.uvue` 主链路
  - 当前已补齐消息窗口、历史消息、聊天记录搜索三条消费链路，群聊发送者名称优先显示群昵称
  - 这是已可进入人工测试的真实能力，后续重点转为群主代改入口等增强项

#### 4.3 显示群成员昵称

- 业务价值判断：
  - 当前不建议实现
  - 企业微信的核心诉求是“群内成员身份清晰”，而不是给每个群再加一个用户级开关来控制是否显示昵称
  - 如果聊天气泡、聊天记录、群成员列表本身就应该展示发送者名称，那应作为统一展示规则处理，而不是群设置页开关
- 当前已具备：
  - 仅有前端页面上的 `ref<boolean>` 和本地切换
- 当前缺口：
  - 没有后端字段
  - 没有前端持久化
  - 没有任何实际消费位把该值用于聊天页、聊天记录页、群成员列表
  - 当前代码中已移除页面入口，但能力本身仍未定义存储与消费边界
- 结论：
  - 该项属于“伪能力”，当前轮次应从文档层面明确降级，不纳入实现范围
  - 若未来确实需要，应先定义消费范围：
    - 仅当前设备本地偏好
    - 是否作用于聊天页发送者名称
    - 是否作用于聊天记录页 / 群成员列表
  - 在这些问题没定之前，不应继续推进接口与存储设计

### 2. 设置变更前后端链路

- 前端接口：
  - `shengyu-ui/shengyu-ui-admin-uniappx/api/conversation.uts`
  - `PUT /system/im/conversation/update`
  - body 字段：
    - `chatId`
    - `isPinned`
    - `noDisturb`
- 前端服务：
  - `conversationService.pinConversation(chatId, isPinned)`
  - `conversationService.setMute(chatId, noDisturb)`
- 后端入口：
  - `AppImConversationController#updateConversation`
- 后端服务：
  - `ImConversationServiceImpl#updateConversation`
  - 先更新 `im_chat_user`
  - 再写入 `im_conversation_user_state`
  - 同时分配新的 `cursorVersion`

### 3. 已有能力与约束

- 已有：
  - 会话更新接口已存在
  - `isPinned / noDisturb` 已进入 `AppImConversationRespVO`
  - `/conversation/sync` 已返回会话用户态字段
  - 前端消息页已按 `isPinned / noDisturb` 做展示和排序
- 约束：
  - 设置页必须更新 `chatId` 维度的会话，而不是 `targetId / groupId` 维度的页面临时变量
  - 单聊页入口当前只传 `chatId`，因此设置页必须先从会话服务反查 `targetId`
  - 群聊页若仅持有 `groupId`，必须通过 `get-by-target` 反查出 `chatId`

## 现状结论

- 前端层面：
  - 群聊设置页已经具备 `消息免打扰 / 置顶聊天` 开关
  - 单聊设置页原先还是本地 `ref`，未接真实会话接口，需要统一并轨
- 群管理附加项层面：
  - `群聊邀请确认`：读链路、群设置写链路、申请单链路、管理员审批通过后入群链路已打通

  - `显示群成员昵称`：已从群设置页实施范围移除，不再作为待开发能力
- 后端层面：
  - 权威设置入口应是 `updateConversation`
  - `pinConversation(Long userId, Long conversationId, Boolean isPinned)` 与 `setMute(Long userId, Long conversationId, Boolean noDisturb)` 两个 service 方法仅改 `im_chat_user`，不承担完整跨端同步闭环
  - 因此前端不得把“只改库字段、不推进用户态版本”的内部简化方法当成最终落地方案

## 后端真实落地要求

### P0. 设置接口必须成为权威入口

- 前端所有 `置顶聊天 / 消息免打扰` 修改统一调用：
  - `PUT /system/im/conversation/update`
- 不允许形成多条语义重叠但一致性能力不同的设置入口
- `updateConversation` 必须保证：
  - 更新 `im_chat_user.is_pinned / no_disturb`
  - 同步写入 `im_conversation_user_state`
  - 推进 `cursorVersion`
  - 推进或保持正确的 `conversationVersion`
  - 后续端侧可通过 `/conversation/sync` 拉到最新设置

### P0. 跨端一致性闭环必须成立

- 设置成功后，当前端立即生效只是第一层
- 真正完成落地还必须满足：
  - 同账号多端能收到这次会话状态变更
  - 断网重连后 `/conversation/sync` 能恢复该状态
  - 重进消息页排序和免打扰 icon 不回滚
- 推荐服务端补齐：
  - 在 `updateConversation` 成功后，向当前用户所有在线 WS 连接推送 `SYSTEM_NOTIFY`
  - payload 至少透传新的 `cursorVersion`
  - 端侧收到后按既有逻辑触发 `syncConversationsIncrementally(false)`

### P0. 用户态版本语义不允许被破坏

- 不允许改动以下字段既有权威语义：
  - `cursorVersion`
  - `conversationVersion`
  - `lastReadSequence`
  - `lastMessageSequence`
- 其中：
  - `cursorVersion` 负责用户维度增量拉取游标
  - `conversationVersion` 负责同 chat 快照合并的幂等与乱序保护

### P1. 群管理设置应按独立群设置链路推进

- `群聊邀请确认` 不应复用会话设置接口，应走群设置接口：
  - 推荐继续使用 `PUT /system/im/group/update`
  - 当前已接入 `AppImGroupUpdateReqVO.needApproval / allowMemberInvite`
  - 当前已接入 `ImGroupServiceImpl#updateGroup` 对 `needApproval / allowMemberInvite` 的写入
  - 当前已闭环到“审批开关打开后，生成申请单并由管理员审批”
  - 后续重点转为通知补强与审批运营能力
- `允许成员邀请` 同样属于群设置接口管理范围：
  - 推荐继续使用 `PUT /system/im/group/update`
  - 仅群主/管理员可调整
  - 只影响普通成员主动添加成员的权限，不影响群主/管理员拉人
- `我在本群的昵称` 不应塞进 `updateGroup`，应走群成员设置接口：
  - 推荐新增 app 接口，例如 `PUT /system/im/group/member/set-nickname`
  - 当前已落地 `PUT /system/im/group/member/set-nickname`
  - 支持 `memberUserId` 为空时设置自己的群昵称
  - 群主设置他人群昵称仍保留现有 service 权限语义
- `显示群成员昵称` 当前不进入接口设计，避免为无消费能力的展示开关制造存储负担

### P1. 群管理设置的消费位必须清晰

- `群聊邀请确认` 的消费位应明确限定在：
  - 邀请码校验结果
  - 群二维码页文案与说明
  - 二维码 / 邀请链接入群页提示
  - 入群流程是否进入“待审核”分支
  - 管理员实时收到新的入群申请提醒
  - 申请人实时收到审批结果提醒
- 当前二维码链路现状：

## 有序推进方案

### 第一阶段：前端设置页并轨

- 群聊设置页、单聊设置页全部统一走 `conversationService`
- 返回消息页后立即体现：
  - 置顶分组变化
  - 免打扰图标变化
  - 未读样式变化

### 第二阶段：后端设置闭环核实

- 核对 `AppImConversationController#updateConversation`
- 核对 `ImConversationServiceImpl#updateConversation`
- 核对 `im_conversation_user_state` 是否正确写入：
  - `cursor_version`
  - `conversation_version`
  - `is_pinned`
  - `no_disturb`
- 核对 `/conversation/sync` 返回项是否带出最新设置

### 第三阶段：多端同步补强

- 若当前 `updateConversation` 后没有 WS 通知：
  - 补推 `SYSTEM_NOTIFY`
  - 透传 `cursorVersion`
- 端侧复用现有增量同步逻辑，不另起一套设置同步专线

### 第四阶段：联调验收

- 单聊设置修改后返回消息页，UI 立即变化
- 群聊设置修改后返回消息页，UI 立即变化
- 同账号第二端在线时，能自动同步设置变化
- 杀进程重进后设置不丢失
- 离线一段时间后重连，`sync` 后状态不回滚

### 第五阶段：群管理项补齐

- 补齐 `群聊邀请确认` 审批链路：
  - 当前已完成群设置页切换保存
  - 当前已完成邀请码验证页 / 入群页对 `needApproval` 的消费
  - 当前已完成“申请入群 -> 管理员处理 -> 通过后真正入群”
  - 当前已完成管理员实时通知、申请人结果通知
  - 后续补充项为审批历史运营能力与通知中心展示完善
- 补齐 `我在本群的昵称` 写链路：
  - 当前已完成群设置页可编辑并成功保存
  - 当前已完成群成员列表可见更新
  - 当前已完成消息窗口、历史消息、聊天记录搜索的发送者名称联动
- 补齐 `允许成员邀请` 权限链路：
  - 当前已完成群设置页真实开关
  - 当前已完成普通成员加人入口显隐与目标页准入
  - 当前已完成后端权限语义与前端展示对齐
- 清理 `显示群成员昵称` 伪能力：
  - 从设计与实现范围中移除，避免误导测试与开发

## 验收标准

- 单聊设置页与群聊设置页均显示统一文案：
  - `消息免打扰`
  - `置顶聊天`
- 设置页切换后，不必手动刷新，返回会话页立即可见结果：
  - 置顶聊天进入置顶区
  - 取消置顶后回到普通会话区
  - 免打扰会话显示免打扰 icon
  - 免打扰会话未读按红点规则展示
- 群聊设置页点击 `群文件` 后，进入统一文件总览页，显示 `全部/图片/视频/文件`
- 单聊设置页点击 `文件` 后，进入同一文件总览页，显示 `全部/图片/视频/文件`
- 群聊与单聊点击 `聊天记录` 后，均进入统一聊天记录页
- 统一文件总览页中的 `下载`、`转发` 在 Android、iOS、Web 三端具备可用路径
- `PUT /system/im/conversation/update` 成功后，`GET /system/im/conversation/sync` 能返回该变更
- 同账号多端或重登后，`消息免打扰 / 置顶聊天` 状态不回滚
- `群聊邀请确认` 若后续落地：
  - 群设置页切换后，邀请二维码 / 邀请码验证页能反映最新策略
  - 打开邀请确认后，通过邀请码不会直接入群，而是生成加群申请单
  - 管理员在申请页通过后，申请人真正进入群聊并建立群会话
  - 新申请提交时，群主/管理员在线端能实时刷新待处理状态
  - 审批完成后，申请人在线端能实时收到结果提示
- `允许成员邀请` 若后续落地：
  - 关闭后，普通成员看不到加人入口，且即使直达加人页也会被拦截
  - 开启后，普通成员可进入加人页并直接拉人
  - 群主/管理员无论开关状态如何，始终可以直接拉人
- `我在本群的昵称` 若后续落地：
  - 群设置页修改成功后，重进页面仍能回填
  - 群成员列表显示最新群昵称
  - 群聊消息 / 聊天记录 / 聊天记录搜索中的发送者名称展示与群昵称策略一致
- `显示群成员昵称` 不作为当前轮次验收项
- 后端编译通过，前端入口无死链、无明显布局残留
