# 推送角标设计任务文档

## 文档目标

- 系统性定义 IM 底部 tab 页 `消息 / 通讯录 / 工作台 / 我` 的角标显示逻辑
- 对齐微信 / 企业微信的已知设计习惯，同时结合当前项目真实前后端能力做可落地约束
- 同步梳理各 tab 页内部的角标、红点、未读数字显示策略
- 明确超过 `99` 时的显示规范，避免底层实现和视觉口径分叉

## 结论先行

- 底部 tab 的角标不允许各页面各自维护，必须统一由单一角标服务驱动
- 当前项目唯一已形成基础数据模型的是：
  - 消息总未读：`badgeData.totalUnread`
  - 会话未读：`badgeData.conversationBadges`
  - 工作台菜单角标：`badgeData.menuBadges`
- 当前轮次推荐只落地两类 tab 角标：
  - `消息` tab：数字角标
  - `工作台` tab：数字角标
- 当前轮次不建议给以下 tab 强行做伪角标：
  - `通讯录` tab
  - `我` tab
- `通讯录 / 我` 只有在出现真实、可解释、可点击闭环的待处理事项时，才允许增加红点；在没有真实数据口径之前，不做本地假红点
- 必须区分“多端同步的账号级角标”与“当前设备内的端侧显示态”：
  - `消息` tab：必须多端同步
  - `工作台` tab：建议按多端同步设计
  - `通讯录` / `我`：没有真实数据前不做
  - `标记未读`：当前仅定义为端侧显示态，不扩展为多端同步能力
- 所有数字角标统一使用：
  - `1-99`：显示真实数字
  - `>=100`：显示 `99+`
  - `0`：隐藏
- 所有弱提醒统一使用纯红点，不显示数字

## 一、微信 / 企业微信参考

### 1.1 可借鉴的产品习惯

- 微信 / 企业微信都支持把会话 `标记未读`
  - 企业微信公开资料可见：
    - PC 端可右键会话标记未读
    - Android 可长按会话标记未读
    - iOS 可左滑后标记未读
- 红点与数字应区分强弱提醒：
  - 强时效、需要用户判断积压规模的提醒，更适合数字
  - 弱时效、仅提示“有新变化”的提醒，更适合红点
- 微信在信息过载场景里，会把部分数字提醒降级为纯红点，以降低心理负担

### 1.2 可直接约束当前实现的技术事实

- `uni.setTabBarBadge` 的 `text` 参数“不超过 3 个半角字符”
- 这意味着底部 tab 数字角标必须统一使用 `99+`
- 不允许使用：
  - `100+`
  - `999+`
  - 更长文案

### 1.3 对当前项目的设计推论

- `消息` 是强时效入口，应使用数字角标
- `工作台` 如果代表待办、审批、流程等可积压事项，也适合使用数字角标
- `通讯录` 更接近结构化目录入口，没有真实待处理数据时不应长期挂数字
- `我` 更接近设置与个人中心入口，除非存在必须处理的安全/资料/审核项，否则只适合红点，不适合数字

## 三、底部 tab 角标设计决议

### 3.1 `消息` tab

- 类型：数字角标
- 数据源：`badgeService.totalUnread`
- 口径：
  - 代表“消息域总未处理量”
  - 以服务端总未读为权威
- 同步级别：必须多端同步
- 显示规则：
  - `0`：隐藏
  - `1-99`：显示真实数字
  - `>=100`：显示 `99+`
- 与会话页的关系：
  - 会话列表每项显示自己的未读
  - tab 只显示总数，不重复展开分类
- 与免打扰关系：
  - 免打扰只改变会话项显示样式，不改变 `消息` tab 总未读聚合口径
- 多端要求：
  - A 端已读后，B 端必须在推送或下次同步后同步消失/变小
  - 不允许 A 端已读但 B 端长期保留旧角标

### 3.2 `通讯录` tab

- 当前轮次：不显示角标
- 原因：
  - 当前没有“新的联系人 / 待通过申请 / 新关注 / 组织审批”等统一数据源
  - 页面本身是目录页，不是消息积压页
- 后续只有在出现以下真实能力时，才允许加红点：
  - 新好友申请
  - 入群申请需要我处理
  - 关注申请
  - 组织邀请/待确认
- 未来推荐形态：
  - 默认使用红点
  - 非必要不显示数字

### 3.3 `工作台` tab

- 类型：数字角标
- 数据源：`badgeService.menuBadges` 的聚合值
- 同步级别：建议多端同步
- 当前轮次设计口径：
  - 只聚合“需要处理的待办项”
  - 不把“已办 / 办结 / 我发起的 / 新建流程”计入 tab 角标
- 推荐聚合键：
  - 当前仅聚合 `todo`
- 显示规则：
  - `0`：隐藏
  - `1-99`：显示真实数字
  - `>=100`：显示 `99+`
- 原因：
  - 工作台 tab 角标的核心价值是提醒“还有多少待处理工作”
  - 如果把已办、办结等统计也叠进 tab 角标，会让数字失真、解释成本过高
- 多端要求：
  - 待办是账号级任务，不应因换设备而出现不同数字
  - 最终仍应以服务端返回的 `menuBadges` 为权威

### 3.4 `我` tab

- 当前轮次：不显示角标
- 原因：
  - 当前没有资料补全、安全风险、系统设置待处理等统一数据源
  - 个人中心不应为了“看起来热闹”挂假红点
- 后续若出现真实能力，推荐只用红点，不用数字
- 可接受的未来场景：
  - 安全设置未完成
  - 个人资料待完善
  - 新系统公告必须确认

## 四、多端同步权威决议

### 4.1 状态分层

- 第一层：服务端权威状态
  - 适用：`消息` tab、会话未读、未来的 `工作台` 待办角标
  - 特征：多端同步、断线恢复、重登后不丢失
- 第二层：端侧即时显示态
  - 适用：当前没有服务端接口，但页面需要立刻反馈的状态
  - 特征：允许本地即时生效，但必须明确边界，不伪装成跨端一致
- 当前明确归类：
  - `消息` tab：第一层
  - 会话项未读：第一层
  - `工作台` tab：目标是第一层
  - `标记未读`：当前只能是第二层

### 4.2 哪些必须多端同步

- `消息` tab 总未读：必须
- 会话列表每个会话的真实未读：必须
- `工作台` tab 待办聚合：建议必须
- 工作台页内待办类卡片 badge：建议必须

### 4.3 哪些当前不要做成多端同步

- `通讯录` tab 红点/数字：当前不做
- `我` tab 红点/数字：当前不做
- 右键菜单 `标记未读`：
  - 当前没有对应后端接口
  - 当前文档明确降级为“前端权威显示态”
  - 不得在产品或代码层面把它表述成“多端一致”

### 4.4 `标记未读` 的当前权威定义

- 业务定义：
  - 这是“帮助当前设备用户稍后回来处理”的辅助显示态
  - 不是消息真实未读水位回退
- 当前实现边界：
  - 只影响当前端会话列表与 `消息` 页显示
  - 不回写服务端 read sequence
  - 不改变其他设备显示
- 文案和实现都必须避免暗示：
  - “账号级未读恢复”
  - “跨端同步未读”
  - “服务端重新计算未读”

## 五、tab 内部页面同步策略

### 5.1 `消息` 页内部

- 会话项 badge：
  - `1-99`：显示数字
  - `>=100`：显示 `99+`
  - `0`：隐藏
- 免打扰会话：
  - 有未读时显示红点，不显示数字
- 会话页与底部 tab 的关系：
  - 会话项显示局部未读
  - 底部 tab 显示总未读
  - 两者都由同一角标服务驱动，不允许分别维护

### 5.2 `通讯录` 页内部

- 当前不新增任何 badge
- 顶部分类项：
  - `群组`
  - `关注`
  - `组织`
  - `部门`
  当前均按普通入口处理
- 如果未来出现待处理类数据，再单独定义：
  - 是否挂在分类项右侧
  - 用红点还是数字
  - 点击后是否能进入明确处理页

### 5.3 `工作台` 页内部

- 页面内流程卡片 badge 保留
- 页面内 badge 的规则与 tab 保持一致：
  - `1-99`：显示数字
  - `>=100`：显示 `99+`
  - `0`：隐藏
- 页面内 badge 和 tab badge 的关系：
  - 页面内卡片：显示具体业务项未处理量
  - `工作台` tab：只显示待办聚合量

### 5.4 `我` 页内部

- 当前不新增 badge
- 收藏、扫一扫、设置等入口先保持普通列表项
- 后续若要加提醒，优先考虑：
  - 入口右侧红点
  - 不建议直接在 `我` tab 上展示数字

## 六、超过 99 的统一显示规范

### 6.1 统一规则

- 所有可显示数字的 badge 统一遵循：
  - `1-99`：显示真实数字
  - `>=100`：显示 `99+`
- 不允许按页面各自决定：
  - `100+`
  - `999+`
  - `...`
  - “小红点 + tooltip”

### 6.2 原因

- `uni.setTabBarBadge` 文本长度受限，`99+` 是安全值
- 与微信/企业微信等主流 IM 产品习惯一致
- 视觉宽度稳定，避免 tabBar 或列表 badge 抖动
- 对用户来说，`100` 和 `900` 的紧急感差异并不足以支撑更长显示

### 6.3 纯红点适用范围

- 只提示“有变化”，不强调规模
- 当前推荐用于：
  - `通讯录` tab 的未来待处理提醒
  - `我` tab 的未来待处理提醒
  - 消息页中的免打扰会话

## 七、实现要求

### 7.1 单一状态源

- 底部 tab 角标统一由 `badgeService` 驱动
- 页面内部会话未读统一由：
  - `conversationService`
  - `badgeService`
  协同驱动
- 所有“是否多端同步”的判断，必须先看是否有服务端权威字段/接口，而不是先看页面是否方便实现
- 不允许：
  - 某个 tab 页自己用 `ref` 维护 tab 角标
  - 某个页面直接写死数字
  - 某个页面自行缓存另一份 badge 口径

### 7.2 tabBar 落地建议

- 建议新增统一 `tab-badge-service` 或在 `badgeService` 内补：
  - `syncTabBarBadges()`
  - 统一把 badge 数据映射到底部四个 tab
- 建议映射规则：
  - `消息` index=0 -> `totalUnread`
  - `通讯录` index=1 -> 当前隐藏
  - `工作台` index=2 -> `menuBadges.todo`
  - `我` index=3 -> 当前隐藏
- 调用时机：
  - `badgeService.init()` 后
  - `handleBadgeUpdate()` 后
  - `syncFromServer()` / `forceSync()` 后
  - 本地已读水位推进后
  - 右键菜单 `标记未读/取消标记未读` 后

### 7.3 端侧映射算法

- `消息` tab：
  - 直接消费 `badgeData.totalUnread`
- `工作台` tab：
  - 当前消费 `menuBadges.todo`
  - 若未来存在多个待处理菜单项，可在服务端直接返回聚合键，避免前端再猜测
- `通讯录` tab：
  - 当前始终隐藏
- `我` tab：
  - 当前始终隐藏
- 映射输出统一分三种：
  - `hide`
  - `dot`
  - `text(1-99/99+)`

### 7.4 后端配合要求

- `GET /system/im/badge/get`
  - 继续作为角标全量快照接口
- `BADGE_UPDATE(204)`
  - 继续作为多端同步主通道
- 要求返回语义稳定：
  - `unreadCount` 只表示消息域总未读
  - `conversationBadges` 只表示会话域未读
  - `menuBadges` 只表示业务菜单角标，不混入消息未读
- `menuBadges`
  - 当前优先补齐 `todo`
  - 在没有真实业务值前，不要返回伪造非 0 数据

### 7.5 页面职责边界

- `message.uvue`
  - 负责展示会话角标
  - 不负责重新定义总未读口径
- `contacts.uvue`
  - 当前不承担 badge 逻辑
- `workbench.uvue`
  - 负责展示 `menuBadges` 已映射到页面内卡片的结果
  - 不负责决定底部 tab 的聚合规则
- `profile.uvue`
  - 当前不承担 badge 逻辑
- `badge-service.uts`
  - 负责统一缓存、同步、通知、tabBar 映射
- `conversation-service.uts`
  - 负责会话未读显示态与消息水位协同

### 7.6 开发任务拆解到可开工粒度

#### 前端

- 在 `badge-service.uts` 内新增 tabBar 映射与渲染方法
- 封装统一格式化函数：
  - `formatBadgeText(count) -> '' | '1'...'99+'`
- 封装统一 tab 应用函数：
  - 有数字 -> `uni.setTabBarBadge`
  - 纯红点 -> `uni.showTabBarRedDot`
  - 无提醒 -> `uni.removeTabBarBadge` + `uni.hideTabBarRedDot`
- 在以下时机统一触发：
  - 初始化
  - `BADGE_UPDATE`
  - `/badge/get`
  - 消息已读水位推进
  - 右键菜单 `标记未读` 切换
- 校验工作台页内 badge 与 tab badge 使用同一套 `99+` 格式化规则

#### 后端

- 保持 `/system/im/badge/get` 与 `BADGE_UPDATE(204)` 返回结构一致
- 补齐 `menuBadges.todo`
- 未补齐的菜单键不返回伪数据
- 若未来需要 `通讯录` / `我` 红点，必须先给出明确字段和业务解释，再进入实现

#### 联调

- 验证多端 A/B：
  - A 端读消息
  - B 端 tab 与会话角标同步变化
- 验证工作台待办：
  - 服务端返回 `todo`
  - tab 与页内卡片同步变化
- 验证 `标记未读`：
  - 当前设备立即生效
  - 其他设备不要求同步
  - 文案与行为不冲突

  - 仅在存在真实待办时显示数字
  - 超过 99 显示 `99+`
  - 换设备后显示口径一致
- `通讯录` tab：
  - 当前无伪角标
- `我` tab：
  - 当前无伪角标
- `消息` 页内部：
  - 普通会话显示数字未读
  - 免打扰会话显示红点
  - 会话数字超过 99 显示 `99+`
- `工作台` 页内部：
  - 流程卡片 badge 超过 99 显示 `99+`
- tabBar 与页内显示口径一致：
  - 同一份数据变化后，不需要手动刷新即可更新
- `标记未读`：
  - 当前设备立即生效
  - 不要求其他设备同步
  - 不影响服务端真实未读水位
- 断线重连后：
  - `消息` tab 与会话未读能由 `/badge/get` 或推送恢复正确值
  - `工作台` tab 能由 `/badge/get` 或推送恢复正确值
