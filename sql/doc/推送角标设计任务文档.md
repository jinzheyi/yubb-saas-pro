# 推送角标设计任务文档

## 文档目标

- 结合当前 `uni-app x + IM + 系统通知` 的真实代码基线，重新定义底部 tab `消息 / 通讯录 / 工作台 / 我` 的角标推进策略
- 明确本轮哪些已经落地、哪些只预留能力、哪些需要等待业务接口补齐
- 统一数字角标、红点、端侧显示态、多端同步态的实现边界

## 结论先行

- 底部 tab 角标必须统一由单一角标服务驱动，不允许页面各自维护
- 当前正式落地且必须多端同步的只有：
  - `消息` tab 数字角标
  - 会话列表单会话未读
- `工作台` 当前调整为：
  - 保留 `menuBadges` 数据模型
  - 保留 `BADGE_UPDATE(204)` 与 `/system/im/badge/get` 的扩展位
  - 当前不显示 tab 角标，不接真实业务值
- `通讯录` 当前已接入真实红点能力：
  - 群加群申请相关系统通知事件
  - 群待审批申请数量接口
  - 当前用户管理群的待处理申请聚合结果
- `我` 当前不做假红点，但建议预埋：
  - `设置 > 检查更新`
  - 后续版本更新通知 / 系统公告确认提醒
- 所有数字角标统一规则：
  - `0`：隐藏
  - `1-99`：显示真实数字
  - `>=100`：显示 `99+`
- 所有弱提醒统一使用红点，不显示数字

## 一、当前代码基线

### 1.1 底部 tab

- 当前 tab 配置位于 `shengyu-ui/shengyu-ui-admin-uniappx/pages.json`
- 四个入口分别为：
  - `pages/message/message`
  - `pages/contacts/contacts`
  - `pages/workbench/workbench`
  - `pages/profile/profile`

### 1.2 统一角标数据模型

- 前端统一角标模型位于：
  - `shengyu-ui/shengyu-ui-admin-uniappx/services/badge-service.uts`
- 当前模型已支持：
  - `totalUnread`
  - `conversationBadges`
  - `menuBadges`
  - 本地缓存
  - `BADGE_UPDATE(204)` 推送
  - `GET /system/im/badge/get`

### 1.3 当前真实可用能力

- `消息` 域：
  - 后端已具备总未读与单会话未读
  - 前端消息页已具备未读数字、免打扰红点、已读水位推进
- `通讯录` 域：
  - 通讯录主页面不单独维护 badge 接口
  - 当前通过统一 `badgeService.menuBadges` 消费群申请聚合红点
- `工作台` 域：
  - 页面内部卡片支持 badge 渲染
  - 但业务模块当前不接入，不应强行显示 tab 角标
- `我` 域：
  - 当前没有 badge 数据源
  - `设置` 页面目前仅有“聊天气泡”入口，适合后续增加“检查更新”

## 二、本轮设计决议

### 2.1 `消息` tab

- 类型：数字角标
- 数据源：`badgeService.totalUnread`
- 权威口径：服务端消息域总未读
- 同步级别：必须多端同步
- 本轮状态：正式落地

### 2.2 `通讯录` tab

- 当前类型：红点
- 当前数据源：
  - `menuBadges.contactsGroupJoinRequest`
- 当前业务口径：
  - 当前用户作为群主/管理员时，自己管理的全部群待处理入群申请总数
- 当前落地形态：
  - tab 只挂红点，不显示数字
  - 通讯录页 `群组` 分类项同步挂红点
  - 点击 `群组` 后，在 `我的群组` 中展示每个可管理群的待处理入口
- 设计约束：
  - 不做本地假红点
  - 只使用服务端权威聚合结果

### 2.3 `工作台` tab

- 当前类型：不显示 tab 角标
- 原因：
  - 业务模块暂时不会接入
  - 当前只允许预留对接能力，不允许落伪数据
- 保留内容：
  - `menuBadges` 数据结构
  - `/system/im/badge/get` 返回结构中的 `menuBadges`
  - `BADGE_UPDATE(204)` 中的 `menuBadges`
  - 前端工作台页内部 badge 渲染能力
- 后续接入条件：
  - 业务方确认真实字段
  - 明确聚合口径
  - 明确是否需要多端同步

### 2.4 `我` tab

- 当前类型：不显示 tab 角标
- 当前原因：
  - 没有真实“必须处理”的账号级事项
- 后续推荐场景：
  - 检查更新
  - 新版本强提醒
  - 系统公告待确认
  - 安全设置待完成
- 推荐形态：
  - 默认红点
  - 除非确有积压规模价值，否则不显示数字

## 三、各模块可推进的真实埋点

### 3.1 `消息` 模块

- 已有完整落地基础：
  - 会话总未读
  - 单会话未读
  - 免打扰红点
  - 已读回写
  - 重连后 `/badge/get` 全量恢复
- 本轮补强：
  - `BADGE_UPDATE(204)`、`/badge/get`、手动同步统一走快照覆盖语义，避免旧值残留
  - 本地 badge 缓存按 `tenantId + userId` 隔离，避免跨账号串数据
  - App 回前台时增加静默 `badge` 鲜度校准，降低断线/多端期间错过推送后的陈旧未读
- 当前对应代码：
  - `pages/message/message.uvue`
  - `pages/message/chat.uvue`
  - `services/badge-service.uts`
  - `services/message-service.uts`

### 3.1.1 会话数据治理补充

- 本轮排查确认：
  - 会话列表出现“未知”并非页面文案问题，而是单聊会话数据本身存在异常
  - 历史问题主要来自两类：
    - 聊天路由 `targetId` 早期存在双重编码，曾可能形成错误的 `sid:` / `sid%3A` / `sid%253A` 目标标识
    - 服务端在单聊对端用户信息缺失时，可能下发 `targetId` 有值但 `targetName` 为空的会话
- 当前治理策略：
  - 前端 `conversationService` 对以下无效会话统一丢弃，不进入列表、快照恢复、按目标补建、增量同步：
    - `chatId` 为空或 `0`
    - 单聊 `targetId` 为异常 `sid:` 系列值
    - 单聊 `targetName` 为空
    - 群聊 `targetId` 为空或 `0`
  - 后端 `/system/im/conversation/list`、`/system/im/conversation/sync`、单会话详情统一过滤无效单聊，避免登录后再次下发脏数据
  - 前后端均增加无效会话过滤日志，便于后续复测与线上定位
- 设计原则：
  - 页面层不承担脏数据修复责任，只做显示
  - 会话有效性必须在服务层与接口层共同兜底
  - 对历史脏数据优先“拦截下发 + 阻止再生成”，如后续仍有存量异常，再做定向数据清理

### 3.2 `通讯录` 模块

- 已发现的真实埋点：
  - `message-service.uts` 已处理群加群申请相关系统通知事件：
    - `group_join_request_created`
    - `group_join_request_admin_refresh`
    - `group_join_request_processed`
  - 前端已有群申请接口：
    - `/system/im/group/join-request/list`
    - `/system/im/group/join-request/pending-count?groupId=`
  - 前端已有处理页：
    - `pages/message/group-join-requests.uvue`
    - `pages/message/group-settings.uvue`
- 当前已落地：
  - 新增聚合接口：
    - `/system/im/group/join-request/managed-pending-count`
  - 群列表接口补充：
    - `myRole`
    - `pendingJoinRequestCount`
  - 后端 badge 聚合补入：
    - `menuBadges.contactsGroupJoinRequest`
  - 前端展示链路补齐：
    - `通讯录 tab` 红点
    - `通讯录 > 群组` 分类红点
    - `我的群组` 中按群展示待处理入口
- 当前闭环：
  - `通讯录`
  - `群组`
  - `入群申请`
  - 审批完成后由 `BADGE_UPDATE` 或静默 `/badge/get` 回刷

### 3.3 `我` 模块

- 当前真实代码基线：
  - `pages/profile/profile.uvue`
  - `pages/profile/settings.uvue`
  - `设置 > 检查更新` 入口已预埋
  - 本地已存储 `clientVersion`
  - 应用版本配置存在于 `manifest.json`
- 当前缺口：
  - 没有“最新版本查询”接口
  - 没有“版本更新通知”推送事件
  - 没有“检查更新”设置项
- 推论：
  - `我` 模块最合理的第一批提醒入口，是 `设置`
  - 比直接给 `我` tab 挂数字更合理的是：
    - `我` tab 红点
    - `设置` 入口红点
    - `检查更新` 子项文案或红点

## 四、多端同步与端侧显示态

### 4.1 第一层：服务端权威状态

- 适用：
  - `消息` tab
  - 会话未读
  - 未来的真实业务 badge
- 特征：
  - 多端同步
  - 断线恢复
  - 重登后不丢

### 4.2 第二层：端侧即时显示态

- 适用：
  - 当前没有后端权威字段，但页面内需要即时反馈的提示
- 当前明确案例：
  - `标记未读`
- 约束：
  - 不得伪装成“多端一致”
  - 不得回退服务端真实已读水位

## 五、统一显示规范

### 5.1 数字角标

- `0`：隐藏
- `1-99`：显示真实数字
- `>=100`：显示 `99+`

### 5.2 红点

- 只表示“有变化 / 有待处理”
- 不表达规模
- 适用于：
  - `通讯录` 的未来群申请提醒
  - `我` 的未来版本更新提醒
  - 免打扰会话

## 六、当前实现要求

### 6.1 单一状态源

- tab 角标统一由 `badgeService + tabBarBadgeService` 驱动
- 页面内部业务 badge 可以各自消费同一状态源，但不得重新定义口径

### 6.2 当前 tab 映射规则

- `消息` index=0：
  - 显示 `totalUnread`
- `通讯录` index=1：
  - 当 `menuBadges.contactsGroupJoinRequest > 0` 时显示红点
- `工作台` index=2：
  - 当前隐藏，仅预留
- `我` index=3：
  - 当前隐藏

### 6.3 后端要求

- `/system/im/badge/get`
  - 继续作为权威全量快照
- `BADGE_UPDATE(204)`
  - 继续作为 badge 同步主通道
- `menuBadges`
  - 当前只接入真实业务键：
    - `contactsGroupJoinRequest`
  - `工作台` 等其他业务仍不返回伪数据

## 八、验收标准

### 8.1 `消息`

- 有总未读时显示数字
- 超过 `99` 显示 `99+`
- 已读后角标同步消失或变小
- 多端保持一致

### 8.2 `通讯录`

- 仅当自己管理的群存在待处理申请时才出现红点
- 点击路径必须闭环：
  - `通讯录` -> `群组` -> `入群申请`
- 审批完成后红点可通过 `BADGE_UPDATE` 或静默 `/badge/get` 恢复到最新状态

### 8.3 `工作台`

- 当前 tab 不显示角标
- `menuBadges` 结构继续保留，可供未来业务对接

### 8.4 `我`

- 当前 tab 不显示角标
- 后续若接入版本更新提醒，必须先有真实事件或接口
