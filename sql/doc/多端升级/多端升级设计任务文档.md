# 多端升级设计任务文档

## 文档目标

- 本文档服务于“平台端统一管理企业级 IM 多端升级”的建设。
- 文档口径以当前工程真实结构为准，目标是让 AI 或开发同学可直接按文档分阶段开工。
- 本文档覆盖：
  - 平台端后端：`shengyu-module-platform`
  - 平台端前端：`shengyu-ui/shengyu-ui-platform-vue3`
  - 移动端 IM 客户端：`shengyu-ui/shengyu-ui-admin-uniappx`
  - 文件存储底座：平台统一 `infra/file`
  - 外部分发渠道：`App Store`、`AppGallery Connect`

## 时间口径与官方边界

- 本文档中的鸿蒙能力口径，按 2026-04-21 前后可查的 `uni-app x` 与华为官方资料整理。
- 当前关键事实：
  - `uni-app x` 已支持纯血鸿蒙，即 HarmonyOS Next
  - `uni-app x` 鸿蒙开发依赖本地 DevEco Studio，本地编译出包，没有云打包
  - AppGallery Connect 的分发、开放式测试、分阶段发布已支持 HarmonyOS

## 最终设计决议

- 移动端 IM 的“包管理、版本发布、灰度、强更、审计、统计”统一由平台端负责，不放在租户端。
- 后端能力归属 `shengyu-module-platform`，前端管理页面归属 `shengyu-ui-platform-vue3`。
- 文件上传与包文件存储不重复造轮子，统一复用平台现有 `infra/file` / `infra/file-config` 能力。
- App 升级服务端不是单纯“版本号比较接口”，而是完整的“应用发布中心”：
  - 应用主数据
  - 安装包资产
  - 发布单
  - 灰度范围
  - 渠道分发记录
  - 升级检查
  - 审计日志
  - 终端升级事件
- Android 首期以整包升级 `apk` 为主，不做 `wgt` 热更新主方案。
- iOS 首期以 App Store 跳转升级为主，企业签名/MDM 作为后续增强。
- HarmonyOS 首期以 AppGallery 应用市场升级为主，开放式测试 / 分阶段发布纳入平台发布设计。
- Web 首期做“版本探测 + 刷新提示 + 强更拦截”。
- 移动端 IM 客户端只负责：
  - 上报自身版本与设备信息
  - 调用检查更新接口
  - 按返回结果执行下载、安装、跳商店、跳应用市场或刷新
- 租户端不负责包发布管理，但可以消费平台端暴露的文件能力与升级结果。

## 当前工程真实边界

### 1. 平台端职责

- 平台端后端模块：
  - `shengyu-module-platform`
- 平台端前端：
  - `shengyu-ui/shengyu-ui-platform-vue3`
- 平台端已存在的真实业务能力：
  - 平台用户、角色、菜单、租户、租户套餐、OAuth2、通知、字典、短信、邮件
- 平台端前端已有典型 CRUD 页面结构，可直接复用：
  - API 层：`src/api/system/**`
  - 列表页：`src/views/system/**/index.vue`
  - 表单弹窗：`*Form.vue`

### 2. 文件能力边界

- 平台文件管理真实后端入口在 `infra` 模块：
  - `shengyu-module-infra/.../controller/platform/file/FileController.java`
  - `shengyu-module-infra/.../controller/platform/file/FileConfigController.java`
- 平台前端已有文件管理与文件配置页面：
  - `shengyu-ui/shengyu-ui-platform-vue3/src/views/infra/file/index.vue`
  - `shengyu-ui/shengyu-ui-platform-vue3/src/views/infra/fileConfig/index.vue`
- 结论：
  - 安装包文件资产不单独建设新的文件子系统
  - 升级中心只管理“升级语义”和“发布语义”
  - 文件实体继续落 `infra_file`

### 3. 移动端 IM 边界

- 移动端 IM 当前设置页存在“检查更新”入口，但未接真实链路：
  - `shengyu-ui/shengyu-ui-admin-uniappx/pages/profile/settings.uvue`
- 移动端请求前缀为 `/app-api`
- 当前客户端版本仅来自本地 manifest / systemInfo
- `uni-app x` 当前已支持鸿蒙编译目标，ArkTS 引擎运行：
  - `uni-app x` 鸿蒙开发指南已说明 HBuilderX 4.61+、DevEco Studio 5.0.7.210+、鸿蒙 API 14+ 的开发要求
- 当前没有：
  - 最新版本查询接口
  - 版本推送事件
  - 强更拦截逻辑
  - 平台端包发布页面

## 联网调研结论

### 官方能力约束

- DCloud 官方升级中心支持整包升级与资源包更新思路，但：
  - `uni-app x` 的 `app-Android` 不支持 `wgt` 检测，不应把 `wgt` 作为当前主方案。
- `uni-app x` 官方鸿蒙文档明确：
  - `uni-app x` 从 4.61+ 起支持纯血鸿蒙 HarmonyOS Next
  - 鸿蒙端需要本地 DevEco Studio 打包，没有云打包
- HTML5+ Runtime 官方能力可用于 App 升级执行：
  - `plus.runtime.install`
  - `plus.runtime.openURL`
  - `plus.runtime.getProperty`
  - `plus.runtime.version`
- 华为 AppGallery Connect 官方资料明确：
  - 分发服务支持 Android、HarmonyOS
  - 分阶段发布支持 Android、HarmonyOS
  - 开放式测试支持 Android、HarmonyOS
  - AppGallery Connect 可为 HarmonyOS 应用创建 App，并提供分发与测试治理能力

### 对当前项目的正确落地方式

- 不接入整套 `uni-upgrade-center` 后台。
- 只借鉴其“客户端升级决策模型”。
- 升级后台落在你们现有平台端体系中，原因如下：
  - 权限、菜单、审计、平台账号体系已存在
  - 文件上传与存储底座已存在
  - 平台本身就是“管理租户的平台”，移动 IM 包管理理应归平台

## 发布治理模型

企业级方案不能只关心“客户端下载什么”，还要关心“版本是否已经在对应渠道可分发”。

### 第一层：平台发布中心

- 负责业务侧决策
  - 哪个应用
  - 哪个平台
  - 哪个租户/用户/渠道可见
  - 是否强更
  - 是否阻断
  - 发布时间窗

### 第二层：外部分发渠道

- 负责渠道侧实际分发
  - iOS：App Store
  - HarmonyOS：AppGallery Connect
  - Android 商店渠道：可后续逐步接入

### 双层命中原则

- 客户端最终收到更新的前提是：
  - 平台发布中心判定“该用户可见该发布单”
  - 渠道分发状态已满足“可安装/可跳转/可升级”

说明：

- 这套双层模型对鸿蒙尤其重要
- 因为鸿蒙企业级发版不应只看你们自己的发布表，还要看 AppGallery 的测试、分阶段发布、正式上架状态

## 领域模型设计

企业级方案不建议只建一张“版本表”。至少拆成以下 6 个核心实体。

### 1. 应用主表 `platform_app_product`

表示“被平台管理的应用”。

建议支持：

- `shengyu-im-mobile`
- `shengyu-im-harmony`
- `shengyu-im-web`
- 后续其他 App

关键字段：

- 应用编码
- 应用名称
- 应用类型
- 默认平台
- 默认渠道策略
- 是否启用

### 2. 安装包资产表 `platform_app_package`

表示“一个真实上传的安装包或外部商店包引用”。

关键字段：

- 应用编码
- 平台
- 渠道
- 包类型
- 分发模式
- 文件 ID
- 文件名
- 文件大小
- MD5 / SHA256
- 包版本信息
- 商店链接
- 市场应用标识
- 包说明

说明：

- 一个 APK 文件是资产
- 一个 iOS 商店链接也视作一个“可发布资产”
- 一个 HarmonyOS AppGallery 分发资产也视作一个“可发布资产”
- 一个 Web 构建版本记录也视作可发布资产

### 3. 发布单表 `platform_app_release`

表示“某次发布动作”。

关键字段：

- 应用编码
- 关联安装包资产
- 发布标题
- 发布说明
- 是否强更
- 最低支持版本
- 生效时间
- 下线时间
- 状态
- 渠道发布模式
- 渠道发布状态要求

说明：

- 企业级系统真正管的是发布单，不是裸版本号
- 同一个安装包可以发布多次到不同范围

### 4. 发布范围表 `platform_app_release_scope`

表示“谁能收到这个发布单”。

支持：

- 全量
- 指定租户
- 指定用户
- 指定渠道
- 百分比灰度

### 5. 渠道分发表 `platform_app_channel_release`

表示“某个发布单在外部分发渠道上的执行记录”。

为什么鸿蒙必须有这张表：

- HarmonyOS 首期主链路不是本地直装包，而是应用市场分发
- 你们平台自己的发布单状态，不等于 AppGallery 里的可下载状态
- 需要把市场维度的状态纳入模型，否则平台无法解释“为什么后台已发布，但终端还没升级”

关键字段建议：

- 发布单 ID
- 渠道类型
- 外部应用 ID
- 外部版本 ID
- 外部发布单号
- 外部状态
- 分发模式
- 分阶段发布比例
- 开放式测试标记
- 最近同步时间

### 6. 升级事件表 `platform_app_upgrade_log`

表示终端真实行为日志。

支持记录：

- 检查更新
- 命中版本
- 展示弹窗
- 点击立即更新
- 下载开始
- 下载成功
- 下载失败
- 安装拉起
- 商店跳转
- 应用市场跳转
- 刷新成功

- `DRAFT`

## 分端升级策略

### Android

- 首期主方案：整包 APK 升级
- 不使用 `wgt` 作为主链路
- 升级执行流程：
  - 获取升级信息
  - 弹窗确认
  - 下载 APK
  - 校验摘要
  - 拉起安装

企业级要求：

- 记录下载开始/结束/失败
- 下载支持进度展示
- 强更可阻断业务继续使用
- 安装包下载 URL 应支持时效签名

### iOS

- 首期主方案：App Store 跳转
- 平台端维护：
  - `storeUrl`
  - 商店版本号
  - 发布说明
- 强更只做“阻断 + 跳商店”

后续增强：

- 企业签名包
- MDM 分发

### HarmonyOS

- 首期主方案：AppGallery 应用市场升级
- 不把“客户端下载后本地静默安装”作为首期主链路
- 终端执行动作：
  - 检查更新
  - 展示鸿蒙版本说明
  - 跳转 AppGallery 对应详情页或升级入口
- 渠道治理动作：
  - 开放式测试
  - 分阶段发布
  - 正式上架

为什么这样定：

- 当前 `uni-app x` 鸿蒙是 HarmonyOS Next 原生编译链路
- 官方可查资料明确 AppGallery Connect 已支持 HarmonyOS 分发、开放式测试、分阶段发布
- 对企业级团队而言，鸿蒙的稳定升级主链路应优先建立在 AppGallery 渠道治理之上，而不是先假设存在与 Android APK 相同的直装模式

鸿蒙首期执行口径：

- 平台端维护鸿蒙应用与市场分发元数据
- 客户端命中更新后跳应用市场
- 强更时阻断继续使用，并引导用户前往市场更新

鸿蒙后续增强：

- 企业内部包分发
- MDM/企业管控安装
- 原生插件能力打通后再评估是否支持更深的应用内升级能力

### Web

- 管理对象不是安装包，而是构建版本
- 平台端维护：
  - `buildVersion`
  - `buildTime`
  - 是否强刷
  - 发布说明
- 客户端行为：
  - 启动检查
  - 定时轮询
  - 提示刷新或强制刷新

## API 设计

### 一、平台端管理接口

这些接口供 `shengyu-ui-platform-vue3` 使用。

#### 1. 应用管理

- `POST /platform-api/system/app-product/create`
- `PUT /platform-api/system/app-product/update`
- `GET /platform-api/system/app-product/get?id=`
- `GET /platform-api/system/app-product/page`
- `PUT /platform-api/system/app-product/update-status`

#### 2. 安装包资产管理

- `POST /platform-api/system/app-package/create`
- `PUT /platform-api/system/app-package/update`
- `GET /platform-api/system/app-package/get?id=`
- `GET /platform-api/system/app-package/page`
- `PUT /platform-api/system/app-package/enable`
- `PUT /platform-api/system/app-package/disable`

说明：

- 文件上传仍走平台已有 `/infra/file/upload` 或预签名上传
- 包资产表只保存 `fileId/url/hash/versionInfo`
- HarmonyOS 若采用 AppGallery 分发，则包资产还需要保存：
  - `appGalleryAppId`
  - `appGalleryPackageName`
  - `appGalleryVersionName`
  - `distributionMode=APP_GALLERY`

#### 3. 发布单管理

- `POST /platform-api/system/app-release/create`
- `PUT /platform-api/system/app-release/update`
- `PUT /platform-api/system/app-release/publish`
- `PUT /platform-api/system/app-release/offline`
- `PUT /platform-api/system/app-release/rollback`
- `GET /platform-api/system/app-release/get?id=`
- `GET /platform-api/system/app-release/page`

#### 4. 渠道分发协同

- `POST /platform-api/system/app-channel-release/create`
- `PUT /platform-api/system/app-channel-release/update`
- `PUT /platform-api/system/app-channel-release/sync-status`
- `GET /platform-api/system/app-channel-release/get-by-release-id?releaseId=`

说明：

- 这组接口用于管理发布单与外部分发渠道的映射
- 鸿蒙首期重点就是 AppGallery Connect
- 后续 Android 各商店也可复用同一模型

#### 5. 升级统计

- `GET /platform-api/system/app-upgrade-log/page`
- `GET /platform-api/system/app-upgrade-log/summary`

## 灰度与租户策略

这是企业级升级方案的关键部分，不能只做“全量升级”。

### 灰度维度

- 全量
- 指定租户
- 指定用户
- 指定渠道
- 百分比
- 市场分发状态

### 推荐匹配顺序

1. 先按应用、平台、渠道过滤
2. 只看已发布且生效中的发布单
3. 优先命中指定用户
4. 再命中指定租户
5. 再命中指定渠道
6. 再命中百分比灰度
7. 最后命中全量
8. 返回优先级最高且版本最高的一条

对鸿蒙再加一层校验：

9. 若命中的发布单是 `distributionMode=APP_GALLERY`
10. 则还要检查对应的 `channelReleaseStatus` 是否达到可分发状态
11. 若仅处于开放式测试，则终端仅对测试范围用户返回更新

### 租户治理原则

- 平台端可以决定某个租户是否看到某次升级
- 适用于：
  - 大客户定制包
  - 内部测试租户
  - 白名单租户
  - 重点租户风险隔离

鸿蒙补充原则：

- 平台端的“租户灰度”与 AppGallery 的“分阶段发布/开放式测试”是两套过滤条件
- 终端最终命中必须同时满足：
  - 平台端可见
  - AppGallery 渠道侧可见

## HarmonyOS 渠道协同设计

这是本次新增的重点。

### 1. AppGallery Connect 在本方案中的定位

- 不是你们平台发布中心的替代品
- 是鸿蒙分发执行层
- 平台端仍然是企业内部“版本可见性和强更策略”的权威源

### 2. 鸿蒙发布流程建议

1. 平台端创建鸿蒙应用主数据
2. 录入鸿蒙包资产或市场版本资产
3. 平台端创建发布单
4. 平台端创建渠道分发记录
5. 运营在 AppGallery Connect 执行：
   - 开放式测试
   - 分阶段发布
   - 正式上架
6. 平台端同步渠道状态
7. 客户端检查更新时同时参考平台发布单和渠道状态

### 3. 鸿蒙测试阶段设计

首期建议支持三类状态：

- `OPEN_TEST`
- `PHASED_RELEASE`
- `OFFICIAL_RELEASE`

说明：

- `OPEN_TEST`
  - 对应 AppGallery Connect 开放式测试
  - 用于白名单用户或小范围验证
- `PHASED_RELEASE`
  - 对应 AppGallery Connect 分阶段发布
  - 用于渐进放量
- `OFFICIAL_RELEASE`
  - 对应正式上架可全量获取

### 4. 鸿蒙客户端执行建议

- 手动检查更新：
  - 看到鸿蒙版本说明
  - 点击后跳 AppGallery
- 启动静默检查：
  - 推荐更新只提示
  - 强更阻断

### 5. 鸿蒙与平台灰度的关系

企业级最容易出错的点：

- AppGallery 分阶段发布是“市场层灰度”
- 你们平台租户/用户灰度是“业务层灰度”
- 二者不能互相替代

正确做法：

- 平台灰度负责业务隔离和租户控制
- 市场灰度负责渠道放量节奏
- 命中条件取交集

## 审计、观测与风控

### 操作审计

平台端必须记录：

- 谁上传了包
- 谁创建了发布单
- 谁发布
- 谁下线
- 谁回滚

### 渠道审计

对于鸿蒙至少要记录：

- 哪个发布单关联了哪个 AppGallery 应用
- 当前处于开放式测试、分阶段发布还是正式发布
- 最近一次同步状态的时间
- 渠道状态是否与平台状态一致

### 终端升级日志

必须记录：

- 哪个租户
- 哪个用户
- 哪个设备
- 命中了哪个发布单
- 最终是否成功下载/安装/打开商店/打开应用市场/刷新

### 风控要求

- APK 下载地址优先采用时效签名 URL
- 包摘要必须入库
- 强更版本必须配置最低支持版本
- 下线和回滚必须即时生效

鸿蒙补充：

- AppGallery 详情页 / 应用标识必须入库
- 平台端不应在未知渠道状态下向鸿蒙端返回“可升级”
- 若渠道状态同步失败，默认按保守策略处理

## 回滚与停发设计

### 停发

- 发布单状态切换为 `OFFLINE`
- 新请求不再命中该发布单

### 回滚

- 平台端指定回滚目标发布单
- 新请求命中上一稳定版本
- 已经下载但未安装的客户端不强制撤回

说明：

- 企业级回滚关注的是“后续请求不再命中新版本”
- 不追求把已下载到终端的文件撤回

## 验收标准

### 平台端

- 可以新增一个 IM 应用
- 可以上传 Android 包并绑定版本信息
- 可以为 iOS 录入商店地址
- 可以为 HarmonyOS 录入 AppGallery 分发信息
- 可以发布一条仅对指定租户可见的更新
- 可以下线和回滚

### 移动端

- 手动检查更新能看到真实版本信息
- Android 能完成下载、校验、安装拉起
- iOS 能跳转商店
- HarmonyOS 能跳转 AppGallery
- 强更版本会阻断继续使用

### Web

- 能识别构建版本变更
- 推荐更新可提示刷新
- 强更可阻断并刷新

### 观测

- 平台端可查看升级事件日志
- 可区分检查、命中、下载成功、下载失败
- 可区分鸿蒙开放式测试、分阶段发布、正式发布状态

## 明确不采用的方案

- 不把升级中心放在租户端
- 不把升级元数据塞入 `infra_file`
- 不以 `wgt` 作为 `uni-app x app-Android` 主升级方案
- 不做只靠前端写死下载地址的伪升级
- 不把 HarmonyOS 简单等同于 Android 直装升级模型

## 现状结论

- 你们当前项目已经具备企业级升级中心的大部分底座：
  - 平台端权限、菜单、前后端 CRUD 体系
  - 平台文件管理能力
  - 移动端多端客户端
- 鸿蒙端在当前项目中不应只被视为“多一个 platform 枚举”，而应作为“平台发布中心 + AppGallery 渠道协同”的完整对象建模
- 当前真正缺的是：
  - 平台侧应用/包/发布/灰度领域模型
  - 鸿蒙渠道分发模型
  - 客户端升级执行服务
  - 事件日志与审计观测
- 因此正确路线不是“补一个检查更新接口”，而是建设一个归属平台端的应用发布中心。
