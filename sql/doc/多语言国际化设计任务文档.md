# 多语言国际化设计任务文档

## 1. 文档目标

本文档用于规划 `shengyu-ui/shengyu-ui-admin-uniappx` 与对应后端服务的国际化落地方案，目标不是只做页面静态文案切换，而是完整覆盖以下能力：

- 设置入口：`我 -> 设置 -> 多语言`
- 首期支持：
  - `跟随系统`
  - `简体中文`
  - `English`
- 后续可平滑扩展更多语言
- 前端页面文案国际化
- `pages.json` / `manifest.json` / 框架内置组件和 API 文案国际化
- 后端返回错误提示、业务提示、校验提示国际化
- IM 实时系统通知、持久化系统消息国际化
- 通知模板、推送、异步消息国际化
- Android / iOS / H5 三端一致

这项能力工程量大、影响面广，不适合“见一个页面改一个页面”。必须按统一语言模型、统一协议、统一存储策略推进。

## 1.2 关联文档

为避免“主文档、SQL 草案、命名规范”各自为战，本专题采用一主多从的文档组织方式：

- 主文档：
  - `sql/doc/多语言国际化设计任务文档.md`
  - 负责总体目标、边界、架构、分阶段实施
- 从属文档：
  - `sql/doc/多语言国际化SQL草案.md`
  - `sql/doc/多语言国际化Key命名规范.md`
  - `sql/doc/多语言国际化开工前核对清单.md`

规则：

- 目标、边界、优先级、分层口径，只能以主文档为准
- SQL 字段、索引、建表草案，以 SQL 草案文档为主
- key 命名、eventKey 命名，以命名规范文档为主
- 开工角色分工与前置核对，以开工前核对清单为主
- 从属文档调整后，若影响总体口径，必须同步回写主文档

## 1.2.1 2026-04-21 最终口径变更

- `shengyu-ui-admin-uniappx`、`shengyu-ui-admin-vue3`、`shengyu-ui-platform-vue3` 三端语言统一按设备/浏览器本地缓存
- 不再设计也不再保留用户级 `language_mode` 字段
- 后端只消费当前请求 `Accept-Language` 与 WebSocket `locale`，用于返回当前设备语言下的系统提示、错误提示、系统消息文本
- 用户原始消息、昵称、群名、公告、文件名等业务数据仍保持原文，不因切换语言被翻译
- 本文档中早期“用户语言偏好落库”的历史记录均已废弃；若与本节冲突，以本节为准

## 1.1 设计红线

国际化必须严格区分“用户数据”和“系统文案”。

允许国际化的内容：

- 页面 UI 文案
- 按钮、标题、空态、占位文案
- toast / modal / action sheet
- 后端错误提示、校验提示、业务提示
- 系统消息
- 系统通知
- 模板消息

不允许因为切换界面语言而改变的内容：

- 用户发送的聊天文本
- 用户填写的备注、昵称、群公告、申请理由、评论等业务数据
- 历史消息中的用户原始输入内容
- 文件名、文件说明等用户数据

示例：

- 用户原来发的是 `今天下午三点开会`，切到英文后仍然显示 `今天下午三点开会`
- 系统消息 `你撤回了一条消息`，切到英文后应显示 `You recalled a message`
- 群系统消息 `群主已转让给 xxx`，切到英文后应显示英文版本

结论：

- 本任务是“系统级国际化”
- 不是“聊天内容翻译”

## 2. 先给结论

### 2.1 推荐总体方案

- 前端继续保留当前项目已有的 `store/locale.uts + hooks/useI18n.uts + locales/*.uts` 体系，但升级为“双层语言模型”：
  - `languageMode`：设备本地选择 `system | zh-CN | en`
  - `resolvedLocale`：当前实际生效语言
- HTTP 请求统一带 `Accept-Language`
- WebSocket 连接与会话也需要同步当前有效语言
- 后端所有“面向用户的提示”以“错误码 / 模板键 / 事件键”为主，不再把中文字符串当唯一真相
- 对于“实时 + 持久”的系统消息，禁止只把中文句子直接写入库作为唯一展示内容
  - 必须保存 `eventKey + params`
  - 展示时按当前用户语言渲染
- 首阶段允许兼容旧链路：
  - `CommonResult.msg` 仍然保留
  - 但服务端按 `Accept-Language` 返回本地化后的 `msg`
- 后续增强阶段可增加可选字段：
  - `i18nKey`
  - `i18nArgs`

### 2.2 不建议的方案

- 不建议只在前端本地做页面文案切换
  - 会导致后端错误提示、系统通知、群系统消息仍然是中文
- 不建议把所有服务端 `msg` 都交给前端按中文字符串二次翻译
  - 中文原文会变更
  - 参数化信息难处理
  - 无法覆盖异步通知与持久化消息
- 不建议继续新增大量“直接写中文”的 `throw exception0(..., "中文提示")`
  - 这会持续放大后期改造成本

  - `system_users`

### 3.4 Web 管理端现状

当前管理端 `shengyu-ui/shengyu-ui-admin-vue3` 已具备成熟的前端国际化底座：

- `vue-i18n`
- `element-plus locale`
- `src/store/modules/locale.ts`
- `src/locales/zh-CN.ts`
- `src/locales/en.ts`

已具备：

- 管理端页面文案中英切换
- Element Plus 组件语言切换
- 本地缓存当前语言

当前缺口：

- 管理端和移动端各自维护语言状态，未统一到同一套后端偏好模型
- 管理端同样主要解决的是“前端页面文案”，并未系统解决后端返回 `msg` 的国际化
- 管理端当前默认只有 `zh-CN / en`，也没有正式的 `system` 偏好设计

结论：

- 后端国际化必须设计成“平台能力”，同时服务：
  - uni-app x 移动端
  - Vue3 租户端
  - Vue3 平台端
- 不能只做移动端专用协议

### 3.5 租户端与平台端 Web 的进一步现状

你补充的两个 Web 端信息需要明确写进方案：

1. `shengyu-ui/shengyu-ui-admin-vue3`
   - 租户端
   - 当前已有 `vue-i18n + element-plus locale + 本地 lang cache`

2. `shengyu-ui/shengyu-ui-platform-vue3`
   - 平台端
   - 同样已有 `vue-i18n + element-plus locale + 本地 lang cache`

两端共同点：

- 都支持 `zh-CN / en`
- 都通过本地缓存保存当前语言
- 都主要解决了前端页面国际化
- 当前 axios/request 层均未统一发送 `Accept-Language`

这带来的结论是：

- 本次后端国际化设计必须同时兼容三类前端：
  - 移动 IM 端
  - 租户 Web 端
  - 平台 Web 端
- 语言请求头必须成为统一协议，而不是某个端的私有实现

## 4. 联网调研结论

### 4.1 uni-app 官方国际化设计要点

根据 uni-app 官方国际化文档与语言 API 文档，当前项目应重点吸收以下设计点：

#### 4.1.1 国际化分层

uni-app 官方明确把国际化拆为两部分：

- 应用部分：
  - 开发者自己的页面和业务代码
- 框架部分：
  - 框架内置组件和 API 涉及界面的部分

这意味着本项目不能只改 `useI18n`。

#### 4.1.2 页面与脚本文案

官方推荐页面和脚本内容使用国际化资源文件，通过 `uni.getLocale()` 获取当前语言。

对当前项目的直接含义：

- 现有 `locales/*.uts + t()` 可以继续保留
- 不需要推翻重来
- 但要补齐和 `uni.getLocale()/uni.setLocale()/uni.onLocaleChange()` 的协同

#### 4.1.3 `pages.json` / `manifest.json` 国际化

官方文档明确：

- `pages.json` 中原生导航栏、原生 tabBar 文案应走项目根目录 `locale/*.json`
- `manifest.json` 也支持通过 `locale/uni-app.<语言代码>.json` 与占位符方式国际化

对当前项目的直接含义：

- 设置页里切换语言后，不能只刷新业务页文字
- 原生标题、TabBar、应用名等也要进入方案

#### 4.1.4 框架内置组件和 API 国际化

官方文档明确：

- `picker`
- `showModal`
- 等界面相关基础组件与 API 也有国际化
- App / H5 自 `3.1.5+` 起支持框架国际化

对当前项目的直接含义：

- `uni.showActionSheet`
- `uni.showModal`
- 框架内置上传/选择器等

这些不能完全依赖业务自翻译，要同时让框架语言切换生效。

#### 4.1.5 语言 API

官方提供：

- `uni.getLocale()`
- `uni.setLocale(locale)`
- `uni.onLocaleChange(callback)`

并说明：

- `uni.getLocale()` 在未显式设置时，会返回根据系统语言自动选择的语言
- `uni.setLocale()` 仅可设置为框架内置语言与自定义扩展语言，遵循 BCP47
- `uni.onLocaleChange()` 用于监听应用语言切换

对当前项目的直接含义：

- 语言 store 不能只停留在 `uni.setStorageSync`
- 必须把 `uni.setLocale()` 纳入主链路
- 必须监听 `onLocaleChange`，否则“跟随系统”模式下三端行为不完整

### 4.2 企业微信 / WeCom 设计思路

#### 4.2.1 能找到公开来源支撑的事实

基于 WeCom App Store 页面，可确认：

- WeCom 已支持多语言
- App Store 展示为 `English + 10 more`
- 更新日志明确提到：
  - `Optimized Internationalization Experience`
  - `Supports 11 interface languages`
  - 海外成员、跨语言翻译、跨时区协作等一并被纳入产品能力

这说明企业微信不是把“界面语言切换”单独看待，而是把它放进企业国际协作能力体系中。

#### 4.2.2 基于产品行为的合理推断

下面是设计推断，不应写成官方事实：

- 语言入口通常放在“我/个人中心 -> 设置”下，而不是散落在登录页或调试页
- `跟随系统` 会排在第一优先级选项
- 切换语言应即时生效，且尽量不要求重新登录
- 用户显式选择语言后，应长期持久化
- 与 UI 语言相邻但不同的能力会单独设计：
  - 聊天翻译
  - 文档翻译
  - 邮件翻译
  - 会议字幕翻译

对本项目的启示：

- “界面语言”与“消息翻译”必须分层
- 首期先做 UI / 系统提示 / 系统消息国际化
- 不要把“聊天内容翻译”混进当前任务

## 5. 目标设计

### 5.1 首期目标

- 设置页提供：
  - `跟随系统`
  - `简体中文`
  - `English`
- 切换后当前端立即生效
- 重启应用后仍保留用户选择
- 登录后可从后端恢复语言偏好
- 接口响应的用户提示按当前语言返回
- IM 中的系统提示消息可按当前语言显示
- 不影响现有消息、联系人、登录、设置主链路

### 5.2 二期目标

- 多端同步语言偏好
- 通知模板多语言化
- WebSocket / 推送按会话或设备语言下发
- 后台错误码平台支持翻译维护

### 5.3 非本期目标

- 聊天内容自动翻译
- 文档内容翻译
- 邮件一键翻译
- 机器翻译服务接入

## 6. 统一语言模型

### 6.1 模型拆分

推荐拆成三个概念：

1. `languageMode`
   - 设备本地选择模式
   - 枚举值：
     - `system`
     - `zh-CN`
     - `en`

2. `resolvedLocale`
   - 当前设备 / 当前会话真实生效语言
   - 例如：
     - `zh-CN`
     - `en`

3. `frameworkLocale`
   - 传给 uni-app 框架的语言代码
   - 建议映射：
     - `zh-CN -> zh-Hans`
     - `en -> en`

### 6.2 为什么要拆

- 用户选择的是“模式”，不是每次都直接等于实际语言
- `跟随系统` 下，不同设备的系统语言可能不同
- uni-app 框架语言代码和项目现有业务语言代码并不完全一致

### 6.3 建议落地方式

- 业务层 canonical locale 继续保留：
  - `zh-CN`
  - `en`
- 新增转换函数：
  - `toFrameworkLocale()`
  - `fromSystemLocale()`

这样可以兼容当前已有 `locales/zh-CN.uts` / `en.uts`，避免一次性把全项目键名和目录改成 `zh-Hans`。

## 7. 前端方案

### 7.1 设置入口与交互

入口：

- `我 -> 设置 -> 多语言`

交互要求：

- 列表项：
  - `跟随系统`
  - `简体中文`
  - `English`
- 当前项右侧显示选中态
- 点击后立即切换
- 轻提示文案本身也要国际化
- 切换过程中不强制用户重新登录

体验原则：

- 与主题设置、聊天气泡设置保持同级风格
- 语言切换结果应尽量一次完成，不要连续弹多个 toast

### 7.2 前端 store 改造

当前 `store/locale.uts` 建议升级为：

- 存储键：
  - `LANGUAGE_MODE`
- 暴露能力：
  - `getLanguageMode()`
  - `setLanguageMode(mode)`
  - `getResolvedLocale()`
  - `resolveLocale(mode, systemLocale)`
  - `applyLocale(resolvedLocale)`
  - `subscribeLocaleChange(listener)`

关键点：

- `applyLocale()` 内部同时做：
  - 更新本地响应式状态
  - 调用 `uni.setLocale(frameworkLocale)`
  - 更新业务翻译资源状态
- `system` 模式下要监听 `uni.onLocaleChange()` 与系统语言变化

### 7.3 根级 locale 资源补齐

项目根目录应新增或补齐官方要求的 `locale/` 目录，用于：

- `pages.json`
- `manifest.json`
- 原生导航栏 / TabBar

建议结构：

```text
shengyu-ui/shengyu-ui-admin-uniappx/
├── locale/
│   ├── zh-Hans.json
│   ├── en.json
│   ├── uni-app.zh-Hans.json
│   └── uni-app.en.json
├── locales/
│   ├── zh-CN.uts
│   └── en.uts
```

职责划分：

- `locale/*.json`
  - 交给 uni-app 框架消费
- `locales/*.uts`
  - 交给业务层 `t()` 消费

### 7.4 请求头语言透传

`utils/request.uts` 统一增加：

- `Accept-Language: <resolvedLocale>`

建议同时预留：

- `X-Locale-Mode: system|zh-CN|en`

说明：

- 服务端真正决定返回哪种语言，首要依据是 `Accept-Language`
- `X-Locale-Mode` 主要用于排障、日志、灰度观察，可选

### 7.5 Toast / Modal / Empty / ActionSheet 统一清理

当前项目里大量存在：

- `uni.showToast({ title: '加载失败' })`
- `uni.showModal({ title: '提示', content: '...' })`
- 页面内直接写中文标签

建议新增一层轻量封装：

- `utils/ui-i18n.uts`

封装目标：

- `showI18nToast(key, params?)`
- `showI18nModal(titleKey, contentKey, params?)`

这样可以减少未来继续写死中文的问题。

### 7.6 设备级语言同步

当前最终口径为“语言跟设备/浏览器走，不跟用户走”。

建议前端启动流程：

1. 未登录：
   - 直接按本地缓存或系统语言决定当前语言
2. 已登录：
   - 仍然只按当前设备本地缓存语言快速回显
   - 不再调用用户资料接口恢复语言

说明：

- 用户资料接口不再返回 `languageMode`
- 不再提供“更新当前用户语言偏好”接口
- 当前设备切换语言后，只影响当前设备；其它设备保持自己的本地设置

## 8. 后端方案

### 8.1 语言解析入口

所有 HTTP 请求应支持从请求头解析语言：

- `Accept-Language`

推荐落点：

- Web 层过滤器 / 拦截器
- 将解析结果写入 `LocaleContextHolder`

解析规则建议：

1. 显式支持：
   - `zh-CN`
   - `zh`
   - `zh-Hans`
   - `en`
   - `en-US`
2. 统一归一化为：
   - `zh-CN`
   - `en`
3. 未识别时回退：
   - `zh-CN`

### 8.2 错误提示国际化

#### 8.2.1 当前问题

现在后端错误提示来源分成四类：

1. `ErrorCode.msg`
2. `ServiceExceptionUtil.MESSAGES`
3. `GlobalExceptionHandler` 里直接写中文
4. `exception0(code, "中文")` 直接写死

这四类必须统一。

#### 8.2.2 推荐方案

第一阶段：

- 保持 `CommonResult` 契约不变：
  - `code`
  - `msg`
  - `data`
- 但 `msg` 改为按 `LocaleContextHolder` 动态解析出的本地化文案

第二阶段：

- 可选增加非破坏性字段：
  - `i18nKey`
  - `i18nArgs`

例如：

```json
{
  "code": 40401,
  "msg": "Group does not exist",
  "i18nKey": "im.group.not_exists",
  "i18nArgs": {},
  "data": null
}
```

意义：

- 老前端继续吃 `msg`
- 新前端可以在特殊场景使用 `i18nKey`
- 便于日志和可观测性统一

#### 8.2.3 推荐存储策略

基于当前项目已有“错误码平台”能力，推荐新建错误码翻译表，而不是把多语言文案继续塞回 Java 常量。

注意：

- 当前 `platform_error_code` 是平台级全局资源，不是租户级资源
- 因此错误码翻译表默认也应是平台级
- 不建议首期给错误码翻译表加 `tenant_id`
- 否则同一个错误码在不同租户下会出现语义漂移，增加维护成本

推荐表：

- `platform_error_code_i18n`

建议字段：

- `id`
- `error_code_id` 或 `code`
- `locale`
- `message`
- `creator`
- `create_time`
- `updater`
- `update_time`

缓存策略：

- 启动时 / 定时拉取缓存
- 按 `code + locale` 建立缓存

回退顺序：

1. 翻译表命中
2. `ServiceExceptionUtil.MESSAGES`
3. `ErrorCode.msg`
4. 全局默认语言

#### 8.2.4 平台化要求

后端错误提示国际化必须作为统一平台能力建设，不能做成“某个端自己传个参数、某几个接口自己判断”的零散实现。

原因：

- 移动端和管理端都需要消费同一套后端接口
- 多租户 SaaS 下，平台层错误提示应该保持统一语义
- 日志、运维、客服排障都需要稳定的错误码，不应因端类型分裂

建议统一能力：

- `LocaleResolver / LocaleContextHolder` 统一解析
- `I18nMessageService` 统一取文案
- `ErrorCodeI18nService` 统一查错误码翻译
- `GlobalExceptionHandler` 统一输出

这样移动端、管理端、开放接口都走同一条链路。

### 8.3 参数校验与全局异常处理

`GlobalExceptionHandler` 必须国际化的点包括：

- 请求参数缺失
- 参数类型错误
- 参数校验失败
- 地址不存在
- 方法不支持
- 上传过大
- 默认 500 错误

建议做法：

- 不再直接拼中文
- 改为调用统一 `I18nMessageService`

例如：

- `web.request.param.missing`
- `web.request.param.invalid`
- `web.request.not_found`
- `web.request.method_not_allowed`
- `web.request.file_too_large`
- `web.request.internal_error`

### 8.4 语言状态存储策略

当前语言状态分三层：

1. 设备/浏览器本地选择
   - `system | zh-CN | en`
   - 由各前端本地缓存
2. 当前请求实际语言
   - HTTP `Accept-Language`
   - WebSocket `locale`
3. 服务端渲染输出
   - 按当前请求语言返回系统提示与系统消息文案

明确不做：

- 不在 `system_users` 增加 `language_mode`
- 不在 `platform_users` 增加 `language_mode`
- 不做用户级语言恢复与跨设备同步

原因：

- IM 与 Web 管理端都存在多端同时登录场景
- 语言偏好本质上更接近设备使用环境，而不是用户主数据
- 若按用户覆盖，会导致“手机切英文，PC 也被动切英文”的体验偏差

### 8.5 多租户 SaaS 的国际化资源分层

这部分必须单独设计，否则后面管理端一起上国际化时很容易混乱。

推荐把国际化资源按“归属域”分为三层：

1. 平台级资源
   - 由平台统一维护
   - 所有租户共享
   - 例如：
     - 全局错误码
     - Web 基础框架文案
     - 通用系统事件键

2. 租户级资源
   - 由租户自己维护
   - 不同租户可不同
   - 例如：
     - 站内信模板内容
     - 某些品牌化通知标题
     - 业务模板文案

3. 设备级偏好
   - 由当前设备自己决定
   - 例如：
     - `languageMode`
     - 主题模式
     - 气泡模式

对应当前工程现状：

- `platform_error_code`
  - 平台级
- `system_notify_template`
  - 租户级
- Web 端浏览器本地 locale cache
  - 设备级
- uni-app 本地 `languageMode`
  - 设备级

结论：

- 错误码翻译不要按租户拆
- 通知模板翻译必须按租户拆
- 语言选择必须按设备主体分别存

### 8.6 建议的数据模型

推荐首期新增或调整如下模型：

1. 平台级错误码翻译表
   - `platform_error_code_i18n`
   - 主键建议唯一约束：
     - `(code, locale)`

2. 租户级通知模板翻译表
   - `system_notify_template_i18n`
   - 字段建议：
     - `id`
     - `template_id`
     - `locale`
     - `title`
     - `content`
     - `tenant_id`
     - `creator`
     - `create_time`
     - `updater`
     - `update_time`
   - 唯一约束建议：
     - `(template_id, locale, tenant_id)`

3. 设备级语言本地缓存
   - uni-app 本地存储
   - Web 浏览器本地缓存

### 8.7 Spring 官方能力的实际落点

结合 Spring / Spring Boot 官方国际化能力，后端建议按下面方式设计：

1. `MessageSource`
   - 作为国际化消息抽象入口
   - 适合承接基础默认文案与回退文案

2. `LocaleContextHolder`
   - 作为当前请求线程语言上下文
   - 所有异常处理、校验处理都从这里取 locale

3. Web 层 Locale 解析
   - 统一解析 `Accept-Language`
   - 写入 `LocaleContextHolder`

4. Validation 国际化
   - Bean Validation 的 message 可走消息源
   - 避免参数校验继续只返回中文

5. 业务消息服务
   - 项目层新增 `I18nMessageService`
   - 先查数据库翻译
   - 未命中再回退到 Spring `MessageSource`

这样能兼顾：

- 数据库可运营维护
- Java 常量可做兜底
- 多端共享同一套后端语义

### 8.8 Web 请求层统一协议要求

无论是：

- `shengyu-ui-admin-vue3`
- `shengyu-ui-platform-vue3`
- `shengyu-ui-admin-uniappx`

请求层都应统一增加：

- `Accept-Language: <resolvedLocale>`

推荐值统一为：

- `zh-CN`
- `en`

不建议让三个端分别约定不同格式。

统一之后，后端可以做到：

- 同一接口
- 同一错误码
- 仅因请求语言不同，返回不同语言 `msg`

这也是避免后面“移动端能国际化、管理端不行”最关键的一层协议约束。

## 9. IM、系统通知与异步消息方案

这是本项目国际化最容易“做偏”的地方。

### 9.0 业务数据与系统数据边界

IM 场景必须先分层：

1. 用户内容
   - 用户自己输入、上传、编辑的数据
   - 永远按原始内容展示
   - 切换界面语言后不改写

2. 系统内容
   - 系统生成的提示、状态、通知、群事件消息
   - 按当前语言渲染

落地判定标准：

- 如果内容来自用户输入框、表单、上传元数据，则按“用户内容”处理
- 如果内容来自系统事件、异常处理、模板拼装、服务端规则产出，则按“系统内容”处理

因此：

- `你撤回了一条消息`
- `对方撤回了一条消息`
- `群主已转让给 xxx`
- `xxx 加入了群聊`
- `你被移出了群聊`

这些都应视为系统内容，允许国际化。

- `你好`
- `请明天前提交合同`
- `群公告：周五团建`
- `申请加入研发群`

这些都属于用户内容，不应因为切换语言而改变。

### 9.1 HTTP 接口返回国际化

这一层相对简单：

- 每次请求都带 `Accept-Language`
- 服务端按请求语言返回 `msg`

适用：

- 接口错误提示
- 同步接口中的业务提示

### 9.2 WebSocket 实时通知国际化

仅靠 HTTP 头不够，因为 WebSocket 是长连接。

推荐方案：

- WebSocket 建连后，在认证或握手阶段同步当前 `resolvedLocale`
- 服务端把 locale 绑定到 session

建议消息位置：

- `AUTH_REQ.extra`
- 或握手 query/header

这样服务端推送：

- `SYSTEM_NOTIFY`
- `BADGE_UPDATE`
- 流程提醒
- 待办提醒

时，能按会话语言处理。

### 9.3 持久化系统消息国际化

这部分必须单独强调：

#### 错误做法

- 把 `群主已转让给“xxx”` 直接以中文写进消息内容表
- 把 `你撤回了一条消息`、`对方撤回了一条消息` 直接以中文写进消息内容表

问题：

- 英文用户永远只能看到中文
- 后期补国际化只能重刷历史数据，代价极高
- 还会把系统文案和用户内容混在一起，后续边界越来越乱

#### 推荐做法

对于系统消息、系统提示消息、群事件消息，持久化时保存“语言无关事件”：

- `eventKey`
- `eventParams`

例如：

```json
{
  "eventKey": "im.system.group_owner_transferred",
  "eventParams": {
    "newOwnerName": "Alice"
  }
}
```

渲染策略可二选一：

1. 服务端读取消息列表时按请求语言渲染 `content`
2. 前端读取 `eventKey + params` 本地渲染

当前项目更推荐：

- 服务端返回：
  - `content`
  - `eventKey`
  - `eventParams`
- 前端优先显示服务端已渲染内容
- 新版前端可在必要时自行重渲染

这样兼容性最好。

#### 当前项目建议落点

若现有 `im_message` 已有扩展字段 / `extra` JSON，可优先复用，不强制第一期改表。

推荐在 `extra` 中增加：

- `i18n.eventKey`
- `i18n.params`
- `i18n.version`

适用场景：

- 群主转让
- 成员入群
- 成员退群 / 被移除
- 群解散
- 禁言 / 解禁
- 撤回消息提示
- 审批类系统通知

### 9.4 站内通知模板国际化

当前系统已有通知模板与通知消息能力：

- `NotifyTemplate`
- `NotifyMessage`

这部分不应继续只维护单语内容。

推荐设计：

- 主模板保留业务标识与参数定义
- 新增模板翻译表：
  - `system_notify_template_i18n`

建议字段：

- `template_id`
- `locale`
- `title`
- `content`

模板发送时按：

1. 当前请求语言
2. 用户偏好语言
3. 默认语言

进行选择。

注意多租户边界：

- `NotifyTemplateDO` 当前是 `TenantBaseDO`
- 因此模板翻译表也必须是租户级
- 不允许把 A 租户的通知模板翻译直接给 B 租户复用为同一条业务记录

### 9.5 管理端与移动端共用后端的设计要求

后端国际化落地后，必须能同时支撑：

- 移动端 uni-app x
- Web 租户端 Vue3
- Web 平台端 Vue3

这意味着：

- 接口返回 `msg` 的国际化不能依赖某一个端的私有实现
- 后端不能假设只有 App 会传语言
- 两个 Web 端请求层也应补 `Accept-Language`
- 未来三端的语言偏好应复用同一套后端设计原则，但按不同用户主体落库

推荐原则：

- “用户偏好”由后端存一份
- “当前请求语言”由请求头传一份
- 返回时优先用请求头
- 异步通知时再回退到用户偏好

## 11. 关键技术决策

### 11.1 `CommonResult.msg` 是否保留

结论：

- 保留

原因：

- 当前前端大量依赖 `msg`
- 一次性去掉会造成改造面过大

### 11.2 服务端是否只返回 code，让前端翻译

结论：

- 不建议

原因：

- 会把后端异常、通知、异步链路都转嫁到前端
- 多端、多版本兼容困难

### 11.3 系统消息是否直接存最终文案

结论：

- 不建议

原因：

- 无法按阅读者语言重渲染
- 无法支持未来新增语言

### 11.4 用户偏好是否只存在本地

结论：

- 不建议

原因：

- 登录后换设备体验差
- 服务端异步通知无法依据用户偏好

### 11.5 多租户下国际化资源是否全部租户隔离

结论：

- 不应一刀切

原因：

- 平台级错误码属于平台统一语义，应全局共享
- 通知模板属于租户业务资源，应租户隔离
- Web 管理端语言偏好属于浏览器设备资源，应本地存储
- 移动 IM 语言偏好属于设备资源，应设备本地存储

正确做法是按资源归属分层，而不是所有国际化资源统一带 `tenant_id`。

## 12. 风险与注意事项

### 12.1 最大风险

最大风险不是技术实现，而是“旧代码继续写死中文”。

如果开工后没有约束：

- 新页面继续写中文
- 新异常继续 `exception0(..., "中文")`
- 新系统消息继续直接存中文句子

那么国际化会越做越乱。

### 12.2 必须建立的开发约束

- 新增用户提示必须走国际化 key
- 新增后端错误提示必须走统一消息服务
- 新增系统消息必须优先使用事件键 + 参数
- Code Review 必须检查是否写死中文

### 12.3 兼容性约束

- Android / iOS / H5 都要验证
- `跟随系统` 重点验证：
  - App 冷启动
  - App 前后台切换
  - H5 浏览器语言
- 不同端 `uni.setLocale()` 行为需实测

#### 13.4.7 IM 系统消息 `extra.i18n` 草案

对于系统消息、撤回提示、群事件消息，建议在消息扩展字段中保存如下结构：

```json
{
  "i18n": {
    "version": 1,
    "eventKey": "im.system.message_recalled_by_self",
    "params": {
      "operatorId": "2038793697430458369",
      "operatorName": "马化腾",
      "targetUserId": "2038793697430458369",
      "targetUserName": "马化腾"
    }
  }

```

群主转让示例：

```json
{
  "i18n": {
    "version": 1,
    "eventKey": "im.system.group_owner_transferred",
    "params": {
      "newOwnerId": "2038796635523633155",
      "newOwnerName": "Alice"
    }
  }
}
```

被移出群聊示例：

```json
{
  "i18n": {
    "version": 1,
    "eventKey": "im.system.group_member_removed",
    "params": {
      "operatorId": "2038793697430458369",
      "operatorName": "管理员A",
      "targetUserId": "2038796635523633155",
      "targetUserName": "Bob"
    }
  }
}
```

推荐事件键首批范围：

- `im.system.message_recalled_by_self`
- `im.system.message_recalled_by_other`
- `im.system.group_owner_transferred`
- `im.system.group_member_joined`
- `im.system.group_member_quit`
- `im.system.group_member_removed`
- `im.system.group_dissolved`
- `im.system.group_muted`
- `im.system.group_unmuted`

渲染规则：

1. 用户普通消息
   - 永远显示原文

2. 系统消息
   - 优先读 `content`
   - 若存在 `extra.i18n` 且前端支持，可按当前语言重渲染

3. 老历史消息
   - 若没有 `extra.i18n`，则保持原样展示，不做破坏性兼容改造

验收：

- 同一接口在 `zh-CN` 与 `en` 请求头下返回不同语言 `msg`

#### 13.5.2 任务线 B：设备级语言模型收口

目标：

- 三端统一切到设备级语言模型，不再保留用户级语言字段

核心任务：

- 回收 `system_users.language_mode`
- 回收 `platform_users.language_mode`
- profile 返回移除 `languageMode`
- 删除 `update-language` 类接口

前置依赖：

- 数据库变更评审

阻塞关系：

- 阻塞“旧设计继续写入用户表”
- 不阻塞纯请求头国际化联调

验收：

- 租户 App、租户 Web、平台 Web 均只按当前设备本地语言生效

#### 13.5.3 任务线 C：移动端 uni-app x

目标：

- 设置页可切换语言
- 请求层透传语言
- 页面与系统级提示可切换

核心任务：

- 重构 `store/locale.uts`
- 增加 `languageMode`
- 接入 `uni.setLocale`
- `utils/request.uts` 补 `Accept-Language`
- 设置页新增“多语言”

前置依赖：

- 后端平台底座可并行开发

验收：

- App 端切换语言后：
  - 页面文案切换
  - 原生标题切换
  - 接口错误提示切换

#### 13.5.4 任务线 D：租户 Web 端

目标：

- 复用现有 `vue-i18n` 能力，并把语言透传给后端

核心任务：

- request/axios 层补 `Accept-Language`
- 浏览器本地缓存当前语言
- 不再从个人中心恢复或同步语言

前置依赖：

- 后端平台底座

验收：

- 租户端页面语言切换后，后端 `msg` 同步切换

#### 13.5.5 任务线 E：平台 Web 端

目标：

- 平台端与租户端遵循同构方案，不单独发明一套实现

核心任务：

- request/axios 层补 `Accept-Language`
- 浏览器本地缓存当前语言
- 平台个人中心不再承载语言偏好恢复与更新

前置依赖：

- 后端平台底座

验收：

- 平台端页面语言切换后，后端 `msg` 同步切换

#### 13.5.6 任务线 F：IM 系统消息与通知

目标：

- 系统消息国际化，不碰用户原始聊天内容

核心任务：

- WebSocket session locale
- 系统消息 `eventKey + params`
- 历史消息读取渲染
- 通知模板翻译表

前置依赖：

- 后端平台底座
- 用户偏好模型

验收：

- `你撤回了一条消息`
- `群主已转让给 xxx`
- `你被移出了群聊`

这些系统消息可随界面语言变化；
用户自己发送的中文消息保持原文不变。

#### 13.5.7 推荐并行顺序

第一批可并行：

- 任务线 A：后端平台底座
- 任务线 B：用户偏好数据模型
- 任务线 C：移动端 locale 底座

第二批可并行：

- 任务线 D：租户 Web 端请求头与偏好恢复
- 任务线 E：平台 Web 端请求头与偏好恢复

第三批收口：

- 任务线 F：IM 系统消息与通知国际化

原因：

- 如果先做 IM 系统消息，而底层语言解析、偏好字段、请求头协议还没稳，后面一定返工。

## 14. 最终推荐排期

推荐顺序：

1. 先做文档确认与字段/协议设计确认
2. 先做前端设置入口与语言底座
3. 再做 HTTP 接口国际化
4. 再做用户偏好多端同步
5. 最后做 IM / 通知模板 / 实时消息国际化

不建议顺序：

1. 直接大面积改页面
2. 最后才补协议和系统消息结构

那样一定返工。

## 15. 验收标准

- 设置页可见“多语言”入口
- 支持 `跟随系统 / 简体中文 / English`
- 切换后页面、原生标题、TabBar 文案一致变化
- HTTP 接口错误提示按请求语言变化
- 同一账号在不同设备上可各自保持本地语言，不互相覆盖
- WebSocket 系统通知可按语言展示
- IM 历史系统消息能按当前语言正确显示
- 同一业务事件不再把中文字符串写死为唯一展示内容
- 新增语言时不需要重构已有业务链路
