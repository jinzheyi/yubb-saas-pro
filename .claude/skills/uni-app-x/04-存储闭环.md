# 04 存储闭环

本章覆盖：Storage（`uni.setStorageSync/getStorageSync`）的工程化封装、Key 规范、类型安全、与 IM 业务的典型落点（token/用户信息/草稿/本地索引/缓存）。

## 4.1 现状（仓库对齐）

- 业务 Store：`shengyu-ui/shengyu-ui-admin-uniappx/store/`
  - `store/user.uts`：token、租户、用户信息、权限、角色等
  - `store/locale.uts`：语言
  - `store/group-selection.uts`：群选择等
- 本地缓存（内存 LRU）：`shengyu-ui/shengyu-ui-admin-uniappx/utils/smart-cache.uts`
  - `userInfoCache`（用户信息 LRU + TTL）
  - `globalMessageCache`（会话最近消息缓存）
- 工程化 Storage Wrapper（本项目已落地）：`shengyu-ui/shengyu-ui-admin-uniappx/utils/storage.uts`

## 4.2 规范（Principles）

- **分层**：
  - Storage：用于跨进程/跨重启持久化的小数据（token、开关、索引、配置）。
  - 内存缓存：用于性能优化（LRU/TTL），不得作为“可靠数据来源”。
- **单点写入**：核心 key（token、用户信息）只能由 store 层写入，页面不得直接改 token。
- **类型安全**：避免 `any` 扩散。
  - `uni.getStorageSync` 返回值不稳定且 key 不存在会 fail，调用方必须使用 wrapper 或 try/catch。
- **可迁移**：所有 key 需要命名空间与版本策略，避免后续重构/灰度出现数据污染。

## 4.3 Key 命名约定（项目建议）

### 4.3.1 约定格式

- 统一前缀：`im.`
- 分层：`im.<domain>.<scope>.<name>`

示例：

- `im.auth.access_token`
- `im.auth.refresh_token`
- `im.user.info`
- `im.chat.<chatId>.draft`
- `im.file.local_cache.<fileId>`

### 4.3.2 禁止项

- 禁止使用无语义 key（例如 `a1`、`temp`）。
- 禁止同一语义在多处使用不同 key（会导致读写错乱）。

## 4.4 模板/封装落点（Where & How）

### 4.4.1 强制使用 `utils/storage.uts`

- 已落地 API：
  - `getString/setString`
  - `getJsonObject/setJsonObject`
  - `remove`

使用建议：

- 业务层读取：优先 `getString/getJsonObject`，必须提供默认值。
- 写入对象：统一 `setJsonObject`，避免页面各自 `JSON.stringify`。

### 4.4.2 Store 层与 Storage 的边界

以 `store/user.uts` 为例：

- token/tenantId/deptId/userInfo/permissions/roles 属于“登录态核心数据”，必须由 store 管理。
- 页面层只通过 store 的 getter 获取（例如 `getAccessToken/getTenantId/getUserInfo`），不得直接读写底层 key。

### 4.4.3 内存缓存（smart-cache）与一致性

`utils/smart-cache.uts` 当前提供：

- `UserInfoCache`：LRU + 24h TTL
- `MessageCache`：会话最近消息列表 + messageId 索引

约束建议：

- 内存缓存只用于加速渲染/减少请求次数；当命中失败必须能回源（API 或 Storage）。
- 涉及“必须可恢复”的数据（例如草稿、文件本地索引）不能只放内存缓存。

## 4.5 与 IM 业务的直接落地建议

- **聊天草稿**：必须落 Storage（按 chatId 分 key），避免 App 重启丢失。
- **文件本地索引**：若做 fileId -> localPath 映射，必须落 Storage/DB，并设计清理策略（按大小/时间）。
- **多租户**：store 已将 tenantId 以 string 存储（避免大整数精度丢失），新增涉及 tenantId 的 key 必须包含租户维度或在切租户时清理。

## 4.6 Reviewer Checklist

- 禁止项：
  - 页面直接读写 `ACCESS_TOKEN/REFRESH_TOKEN` 等核心 key
  - 页面散落 `JSON.parse/stringify` 存取对象
  - 用内存缓存替代持久化（导致重启丢数据）
- 必须项：
  - 新增持久化 key 必须遵循命名规范
  - 新增持久化逻辑必须明确生命周期与清理策略
- 推荐项：
  - 需要高频读取的数据先查内存缓存，再回源 API/Storage

## 4.7 常见问题（Troubleshooting）

- **读取 Storage 报错**：确认是否 key 不存在导致 fail；改用 `utils/storage.uts` 兜底。
- **数据被污染/错租户**：检查 key 是否缺少租户维度；切换账号/租户时是否清理旧 key。
- **缓存不生效**：检查是否每次都 new cache（应使用 `smart-cache` 的全局单例）。
