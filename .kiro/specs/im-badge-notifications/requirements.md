# 需求文档: IM消息角标和菜单角标通知

## 简介

本文档规定了企业IM移动应用(shengyu-ui-admin-uniappx)的消息角标和菜单角标实时通知功能需求。系统后端采用 Spring Boot + Netty WebSocket + Protobuf 架构,前端使用 uni-app x (UTS语言)。

WebSocket 中间件已经支持 BADGE_UPDATE (messageType = 204) 消息类型,本 spec 将设计完整的前后端集成方案,实现类似微信的角标通知体验。

## 术语表

- **Badge_System(角标系统)**: 管理和显示未读消息数和菜单角标的系统
- **Message_Badge(消息角标)**: 显示在消息列表、底部导航栏上的未读消息数红点
- **Menu_Badge(菜单角标)**: 显示在工作台菜单项上的待办数量角标
- **Badge_Service(角标服务)**: 处理角标更新逻辑的服务层
- **WebSocket_Badge(WebSocket角标)**: 通过 WebSocket 实时推送的角标更新消息
- **Local_Badge(本地角标)**: 客户端本地计算和维护的角标数据
- **Unread_Count(未读数)**: 会话的未读消息数量
- **Total_Unread(总未读数)**: 所有会话的未读消息总数
- **Badge_Update_Message(角标更新消息)**: Protobuf 定义的角标更新消息类型

## 需求

### 需求1: 消息列表角标显示

**用户故事:** 作为用户,我希望在消息列表的每个会话上看到未读消息数角标,以便我知道哪些会话有新消息。

#### 验收标准

1. 当会话有未读消息时,角标系统应在会话头像右上角显示红色角标
2. 当未读数 ≤ 99 时,角标系统应显示具体数字
3. 当未读数 > 99 时,角标系统应显示 "99+"
4. 当会话开启免打扰时,角标系统应只显示红点,不显示数字
5. 当用户进入会话并阅读消息时,角标系统应清空该会话的角标
6. 当会话未读数为 0 时,角标系统应隐藏角标

### 需求2: 底部导航栏角标显示

**用户故事:** 作为用户,我希望在底部导航栏的"消息"标签上看到总未读数角标,以便我在其他页面时也能知道有新消息。

#### 验收标准

1. 当有未读消息时,角标系统应在"消息"标签图标右上角显示红色角标
2. 当总未读数 ≤ 99 时,角标系统应显示具体数字
3. 当总未读数 > 99 时,角标系统应显示 "99+"
4. 当所有会话都已读时,角标系统应隐藏角标
5. 当收到新消息时,角标系统应实时更新总未读数
6. 当用户阅读消息时,角标系统应实时减少总未读数

### 需求3: WebSocket 实时角标更新

**用户故事:** 作为用户,我希望角标能够实时更新,以便我能立即看到新消息通知。

#### 验收标准

1. 当 WebSocket 接收到 BADGE_UPDATE 消息时,角标系统应解析消息内容
2. 当角标更新消息包含 unreadCount 时,角标系统应更新总未读数
3. 当角标更新消息包含会话级未读数时,角标系统应更新对应会话的角标
4. 当 WebSocket 连接断开时,角标系统应使用本地缓存的角标数据
5. 当 WebSocket 重新连接时,角标系统应从服务器同步最新的角标数据
6. 当角标更新失败时,角标系统应记录错误但不影响其他功能

### 需求4: 菜单角标显示

**用户故事:** 作为用户,我希望在工作台的菜单项上看到待办数量角标,以便我知道有多少待处理的任务。

#### 验收标准

1. 当菜单项有待办数量时,角标系统应在菜单图标右上角显示红色角标
2. 当待办数量 ≤ 99 时,角标系统应显示具体数字
3. 当待办数量 > 99 时,角标系统应显示 "99+"
4. 当待办数量为 0 时,角标系统应隐藏角标
5. 当 WebSocket 接收到菜单角标更新时,角标系统应更新对应菜单项的角标
6. 当用户处理完待办事项时,角标系统应实时减少角标数量

### 需求5: 角标数据持久化

**用户故事:** 作为用户,我希望角标数据能够持久化,以便应用重启后仍能看到未读消息数。

#### 验收标准

1. 当角标数据更新时,角标系统应将数据保存到本地存储
2. 当应用启动时,角标系统应从本地存储加载角标数据
3. 当 WebSocket 连接成功时,角标系统应从服务器同步最新数据并覆盖本地数据
4. 当本地存储失败时,角标系统应记录错误但不影响角标显示
5. 当角标数据过期时,角标系统应清除本地缓存并重新从服务器获取

### 需求6: 角标服务集成

**用户故事:** 作为开发者,我希望角标服务能够与消息服务无缝集成,以便角标能够自动更新。

#### 验收标准

1. 当消息服务接收到新消息时,角标服务应自动增加对应会话的未读数
2. 当消息服务标记消息已读时,角标服务应自动减少对应会话的未读数
3. 当用户进入会话时,角标服务应自动清空该会话的未读数
4. 当用户退出会话时,角标服务应保持未读数不变
5. 当消息服务初始化时,角标服务应从服务器获取初始角标数据

### 需求7: 多端同步

**用户故事:** 作为用户,我希望角标能够在多个设备间同步,以便我在任何设备上都能看到正确的未读数。

#### 验收标准

1. 当用户在设备A阅读消息时,设备B的角标应实时更新
2. 当用户在设备A收到新消息时,设备B的角标应实时更新
3. 当用户在设备A清空未读数时,设备B的角标应实时清空
4. 当设备离线时,角标系统应使用本地缓存的数据
5. 当设备重新上线时,角标系统应从服务器同步最新数据

### 需求8: 性能优化

**用户故事:** 作为用户,我希望角标更新不会影响应用性能,以便应用保持流畅。

#### 验收标准

1. 当角标更新时,角标系统应使用防抖机制避免频繁更新UI
2. 当批量更新角标时,角标系统应合并更新请求
3. 当角标数据量大时,角标系统应使用虚拟化技术优化渲染
4. 当 WebSocket 消息频繁时,角标系统应使用队列机制处理消息
5. 当角标计算复杂时,角标系统应使用 Web Worker 或异步计算

### 需求9: 错误处理

**用户故事:** 作为用户,我希望即使角标更新失败,应用仍能正常使用,以便我不会因为角标问题而无法使用IM功能。

#### 验收标准

1. 当 WebSocket 角标消息解析失败时,角标系统应记录错误并使用本地数据
2. 当服务器返回错误的角标数据时,角标系统应使用默认值
3. 当本地存储失败时,角标系统应使用内存缓存
4. 当角标更新超时时,角标系统应取消更新并保持当前状态
5. 当角标数据不一致时,角标系统应提供手动同步功能

### 需求10: 与现有架构的兼容性

**用户故事:** 作为开发者,我希望角标功能能够与现有的 WebSocket 中间件和消息服务无缝集成,以便不需要大规模重构代码。

#### 验收标准

1. 当实施角标功能时,角标系统应使用 WebSocket 中间件的 BADGE_UPDATE 消息类型
2. 当集成消息服务时,角标系统应使用现有的消息监听器机制
3. 当更新 UI 时,角标系统应使用现有的组件和样式
4. 当存储数据时,角标系统应使用现有的存储工具
5. 当处理错误时,角标系统应使用现有的错误处理机制
