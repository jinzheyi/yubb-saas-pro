## 概述

本实施计划将完整的企业级 IM 消息系统分解为可执行的开发任务。系统基于现有的 WebSocket 中间件构建，实现单聊、群聊、消息类型、消息状态、高级功能、业务通知、实时通话、性能优化、多端同步等完整功能。

### 现有基础设施

**重要**: 以下基础设施已经存在，无需重新开发:

1. **数据库表** (已存在于 `sql/mysql/1.0/im/ddl_im_tables.sql`):
   - ✅ im_message, im_conversation, im_group, im_group_member
   - ✅ im_message_read, im_group_file, im_group_folder
   - ❌ im_call_record, im_notification (需要创建)

2. **文件上传服务** (已实现):
   - ✅ 后端 API: `/app-api/infra/file/upload` (AppFileController)
   - ✅ 前端工具: `utils/upload.uts`
   - ✅ 群文件管理: AppImGroupFileController

3. **角标通知服务** (已实现 - 参见 im-badge-notifications spec):
   - ✅ 后端: ImBadgeService
   - ✅ 前端: BadgeService (services/badge-service.uts)
   - ✅ WebSocket: BADGE_UPDATE 消息处理 (messageType = 204)
   - ✅ UI 集成: message.uvue, index.uvue, workbench.uvue

实施分为以下阶段:
1. 数据库和基础设施搭建
2. 后端核心服务实现
3. WebSocket 中间件 SPI 实现
4. 移动端核心服务实现
5. 消息功能实现
6. 高级功能实现
7. 性能优化实现
8. 离线和多端同步
9. 群组和通话功能
10. 错误处理和边界情况
11. 集成测试和优化
12. 文档和部署

## 注意事项

### 现有基础设施使用

**数据库表**:
- 直接使用 `sql/mysql/1.0/im/ddl_im_tables.sql` 中已定义的表
- 只需创建 im_call_record 和 im_notification 两个新表
- 注意字段名差异: no_disturb (不是 is_muted), name (不是 group_name)

**文件上传**:
- 使用 `utils/upload.uts` 的现有方法上传文件
- 调用 `/app-api/infra/file/upload` API
- 群文件使用 AppImGroupFileController 的专用接口
- 无需重新实现文件上传逻辑

**角标通知** (im-badge-notifications spec 已完整实现):
- 后端使用现有的 ImBadgeService (角标计算和推送)
- 前端使用现有的 BadgeService (services/badge-service.uts)
- WebSocket BADGE_UPDATE 消息 (messageType = 204) 已支持
- UI 组件 (message.uvue, index.uvue, workbench.uvue) 已集成
- 只需在 MessageStorageService 中调用 pushBadgeUpdate() 集成
- 无需重新实现角标功能

**群文件管理**:
- 使用 AppImGroupFileController 的现有接口
- im_group_file 和 im_group_folder 表已存在
- 只需在 UI 层集成调用

### 开发顺序

1. **先后端后前端**: 确保后端 API 稳定后再开发前端
2. **先核心后高级**: 优先实现核心消息功能，再实现高级功能
3. **增量开发**: 每个阶段完成后进行 Checkpoint 验证
4. **持续测试**: 每个功能实现后立即编写测试
