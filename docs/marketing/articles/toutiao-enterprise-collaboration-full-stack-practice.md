很多人第一次做企业即时通讯，路径都很像：先做登录，再做联系人列表，接一条 WebSocket，最后加群聊和音视频。

演示环境里，消息能发送、通话能响铃，似乎系统就已经完成了大半。但真正进入企业协作场景后，困难才刚刚开始：一个员工加入多家企业后，怎么保证切换企业不会串数据？部门、岗位和角色发生变化后，通讯录、群成员、文件权限谁来同步？用户在手机、浏览器同时登录时，通话超时、拒绝、接听怎样让所有设备看到同一个结果？网页能打开，为什么真机依然无法建立音视频连接？

这些问题看起来分散，背后其实是同一个主题：**企业协作系统不是“聊天功能加后台”，而是一套需要同时处理身份、组织、状态、实时连接和网络环境的分布式业务系统。**

本文以一套基于 Spring Boot、Vue 3、Flutter、Netty、Protobuf、LiveKit、MySQL、Redis 和 Docker 的多租户企业协作系统为例，完整拆解从平台管理、企业管理到员工协作端的技术架构、关键实现、部署方法与排障思路。

## 一、先理解产品边界：三类前端，不是三套孤立系统

企业协作系统通常至少有三类入口。

第一类是平台管理端。它面向平台管理员，用于维护租户、套餐、全局配置和平台级能力。这里的重点不是员工聊天，而是让多个企业能够在一套系统中被正确隔离与管理。

第二类是企业管理端。它面向每家企业自己的管理员，维护部门、成员、岗位、角色、菜单、数据权限和企业内部业务。组织结构在这里产生，并成为通讯录和协作范围的上游事实。

第三类是员工协作端。它通过 Flutter 同时覆盖 Android、iOS 和 Web，承担联系人、单聊、群聊、文件、语音、视频、通知和企业切换等员工高频操作。

这三类前端的界面不同，但不应该拥有三份彼此复制的用户体系。正确的关系是：平台端管理企业边界，企业端维护组织与授权，员工端在已授权的企业上下文内进行协作。

换句话说，员工端的通讯录不是另一套“IM 用户库”，而是组织与成员关系在协作场景下的投影。

## 二、多租户的核心不是 tenant_id，而是“当前企业上下文”

多租户项目最容易出现的误解，是认为业务表有一个 `tenant_id` 字段就完成了隔离。实际上，字段只是数据层的起点。真正需要隔离的是一次访问从进入系统到返回客户端的整条链路。

一个更符合企业实际的身份模型可以拆成三层。

第一层是全局账号。用户以邮箱或手机号等凭据登录，它是“这个人是谁”的身份。

第二层是企业成员关系。同一位用户可以创建自己的企业，也可以被邀请或申请加入其他企业。用户与企业之间的关系决定了他是否是成员、是否有效、属于哪个部门、拥有哪些角色。

第三层是当前企业上下文。用户这一次打开 App 或浏览器时，究竟以哪家企业身份工作。联系人、会话、群组、未读数、文件和实时事件都必须落在这个上下文中。

可以把它理解成这样：

全局账号 -> 企业成员关系 -> 当前企业上下文 -> 当前可见数据与可执行操作。

如果只做第一层和第二层，用户能加入多个企业；如果没有第三层，系统就不知道此刻应该展示哪家企业的数据，更无法阻止旧企业的缓存和事件流入新企业页面。

因此，一次完整请求至少需要经过以下判断：

1. 当前 Token 对应哪个用户。
2. 当前请求声明或携带的是哪个企业上下文。
3. 该用户在目标企业是否仍是有效成员。
4. 当前角色、菜单和数据范围允许访问哪些资源。
5. 用户传入的会话、群组、文件或通话资源是否真的属于该企业。

这五步不只服务于普通 HTTPS 接口，同样适用于 WebSocket 鉴权、文件下载、文件预览、通话令牌签发、后台任务和缓存读取。

## 三、切换企业不是刷新页面，而是重建安全作用域

在客户端做“切换企业”时，最常见的错误是只更换一个当前企业名称，再重新请求会话列表。这样做看起来能切换，但旧缓存、旧未读数、旧 WebSocket 订阅依然可能存在。

一次安全的企业切换，建议按以下顺序完成：

1. 客户端提交目标企业标识。
2. 服务端校验用户仍是该企业有效成员，并刷新当前企业上下文。
3. 客户端停止旧企业的实时订阅。
4. 客户端切换本地缓存和内存状态的命名空间。
5. 客户端拉取目标企业的联系人、会话、未读和权限快照。
6. 客户端建立目标企业的实时事件订阅。

本地缓存的键也应该带上用户和企业维度。例如，会话缓存不能只使用 `conversationId`，更稳妥的逻辑是：用户标识 + 企业标识 + 会话标识。未读数、草稿、在线设备信息同样如此。

原因很朴素：同一个人可以在两家企业中与同一位联系人有不同关系，甚至都有单聊。若缓存键没有企业维度，消息草稿、未读数和会话排序都会有串数据风险。

【插图 4：企业切换时序图】

建议图片文字：

用户选择企业 -> 服务端验证成员关系 -> 解除旧 WebSocket 订阅 -> 切换缓存作用域 -> 回拉新企业快照 -> 建立新订阅。

图注建议：**切换企业是安全上下文、缓存命名空间与实时订阅的同步切换。**

## 四、组织与会话必须分开建模：一个是组织事实，一个是协作事实

企业协作中最容易被低估的，是通讯录和会话并不是同一种数据。

部门、岗位、成员、角色属于组织事实。它们决定谁属于企业、谁在什么部门、谁拥有何种权限。

单聊、群聊、群成员、消息、已读、撤回、附件属于协作事实。它们记录谁在一起协作、谁发过消息、谁已阅读、谁还可以继续发言。

把这两类事实分开，会自然得到一组更合理的业务规则：

- 员工调部门后，通讯录结构应当变化，但历史会话和消息不应消失。
- 员工退出群或被移出群后，应停止后续发言能力，但不应从企业通讯录中消失。
- 用户被禁用或离职后，组织状态应成为后续会话、文件、通话授权的上游约束。
- 群聊成员变化需要推送实时事件，但历史消息的保留策略应由业务规则明确，而不是由客户端随意删除。

这也是为什么成熟的企业协作系统不应该通过“同步两张用户表”来维持通讯录。更可靠的路径是：组织模型是权威来源，协作模块消费成员关系和领域事件。

例如，成员被停用后，可以产生“成员状态变化”事件。会话列表、群成员页、实时订阅和文件访问各自根据这个事件刷新自己的有效范围，但不需要复制一份完整组织数据。

【插图 5：组织域与协作域对照图】

左侧：企业 -> 部门 -> 成员 -> 岗位/角色。

右侧：会话 -> 群成员 -> 消息 -> 已读/附件/通话。

中间箭头：成员状态与权限变化通过领域事件影响协作范围。

## 五、HTTP、WebSocket、文件服务、音视频媒体各自解决什么问题

很多项目早期会把越来越多的能力塞进 WebSocket。这样做初期方便，后期会带来连接阻塞、协议难以演进、文件大包影响消息延迟等问题。

更合适的分工是：

HTTPS API 负责登录、组织查询、历史消息、分页列表、配置、上传元数据和权威状态查询。它适合请求响应、权限校验、分页和补偿。

WebSocket 负责新消息、会话更新、已读、在线状态、来电、群成员变化等服务端主动推送事件。它追求低延迟，但不应该是所有数据的唯一来源。

文件服务负责图片、语音、附件的上传、下载和预览。文件内容不应塞进实时消息帧，消息只引用文件元数据。

音视频媒体服务负责房间、媒体协商、音视频轨道、网络穿透和低延迟传输。它不负责企业权限模型，也不应成为通话业务状态的唯一事实来源。

从技术实现上，实时业务事件可由 Netty 和 Protobuf 承载。Protobuf 的价值不仅在于传输更紧凑，更重要的是消息类型、字段编号和兼容规则可以长期演进。移动端和 Web 端不会在同一时刻升级，协议必须允许旧客户端安全忽略未知字段，也允许新客户端对缺失字段使用默认行为。

## 六、实时系统不能假设“事件只到一次，而且一定有序”

移动端切换网络、浏览器休眠、系统将 App 放入后台、服务端短暂重启，都会让实时连接出现重连。重连成功并不等于客户端已经恢复正确状态。

一个更稳妥的实时事件模型，建议至少包含三个字段：

- `eventId`：事件全局唯一标识，用于去重和日志关联。
- `eventType`：明确事件类型，例如消息创建、成员变化、通话结束。
- `occurredAt` 或版本号：用于排序、诊断和识别事件缺口。

客户端处理事件时，可以遵守这样的规则：

第一，已经处理过的 `eventId` 直接忽略。

第二，事件所属企业不等于当前企业作用域时，不写入当前页面状态。

第三，事件版本连续时，只更新局部状态。

第四，发现版本缺口或重放窗口已过期时，不猜测数据，而是调用 HTTPS 接口回拉联系人、会话、未读和成员关系快照。

这种设计的核心不是追求“网络永不丢事件”，而是即使网络不可靠，客户端仍然有回到权威状态的路径。

建议图片文字：

## 七、通话不是一个弹窗，而是一台服务端状态机

音视频功能最常见的误区，是认为“拉起一个媒体房间”就等于完成了通话。实际上，业务通话至少需要区分创建、响铃、接听、连接、拒绝、取消、超时、失败和结束等状态。

一个典型的状态流转如下：

创建呼叫 -> 通知被叫响铃 -> 被叫接听 -> 双方建立媒体连接 -> 任意一方结束。

在这个过程中，还可能发生拒绝、主叫取消、超时、权限被拒绝、网络不可达和媒体房间连接失败。

服务端必须保存 `callId` 和权威状态，而不是把结果交给两个客户端页面自行猜测。这样可以处理最棘手的多端问题：

- 主叫超时取消后，被叫所有在线设备都应停止响铃。
- 被叫在 Web 端接听后，手机端来电页要同步关闭。
- 用户断网重连后，要向服务端查询通话最终状态，而不是恢复旧弹窗。
- 媒体连接失败时，业务服务应将呼叫收敛到失败或结束状态，并通知双方。

业务控制链路与媒体链路应该并行但独立。

业务控制链路负责：创建呼叫、校验成员关系、推送响铃、接听状态、超时、结束、通话历史。

媒体链路负责：浏览器或系统设备权限、进入房间、发布音视频轨道、订阅对方轨道、UDP 或 TURN 网络连通。

媒体连接成功只是业务状态变化的一个输入，不能代替业务状态本身。

【插图 8：通话控制链路与媒体链路双泳道图】

左侧泳道：主叫端 -> 业务服务 -> 被叫端，展示 `callId`、响铃、接听、结束事件。

右侧泳道：主叫端/被叫端 -> RTC 服务，展示设备权限、入房凭据、加入房间、发布和订阅媒体轨道。

图注建议：**控制链路决定“这次通话是否有效”，媒体链路决定“音视频能否建立”。**

## 八、为什么网页能打开，通话仍然失败：音视频需要额外的网络验收

浏览器或 Flutter Web 能加载页面，只能说明 HTTPS 页面资源可达。一次成功通话还需要额外满足多个条件：

1. API 和 WebSocket 域名的 TLS 证书有效，WSS 可以完成 Upgrade。
2. 发起或接听按钮由用户手势触发，浏览器才能正确申请麦克风和摄像头权限。
3. 音视频服务的域名、房间凭据与客户端配置一致。
4. 云安全组和服务器防火墙允许媒体服务实际使用的 TCP、UDP、TURN 和中继端口。
5. 对外公布的媒体节点地址必须是客户端可路由的公网地址，不能暴露 Docker 内部网段地址。

当出现“对方能收到来电，点击接听后一直转圈”时，可以按以下顺序排查：

先检查业务服务中的 `callId` 是否已经从响铃变成接听；再检查客户端是否真正弹出或已获得设备权限；随后检查 WSS、房间凭据和媒体域名；最后检查 UDP、TURN 和运营商网络环境。

这套顺序能把问题快速定位在业务状态、客户端权限、信令连接或媒体网络中的某一层，而不是反复修改页面逻辑。

## 九、Flutter 多端不是“编译三次”，而是处理三种运行环境

Flutter 的价值在于复用业务界面和状态逻辑，但 Android、iOS 和 Web 依旧是不同的运行环境。

Android 和 iOS 更关注系统权限、前后台生命周期、网络切换、本地通知和真实设备音视频能力。

浏览器更关注 HTTPS、安全上下文、WSS、用户手势、浏览器权限策略、资源缓存和 Web 运行时兼容性。

因此，多端设计需要做到“业务规则一致，平台适配不同”。例如，通话的服务端状态机、租户上下文、事件协议和错误码可以共享；而麦克风权限申请、本地存储、后台保活、播放能力和 Web 首屏初始化不能完全按同一种方式实现。

Flutter Web 的性能尤其需要分开看。一次首屏打开通常包括入口 HTML、启动脚本、主 JavaScript 产物、运行时资源、首次 API 请求和实时连接初始化。入口文件负责指向当前版本，不宜设置过长缓存；版本化静态资源可以长缓存；缓存预热、实时连接和媒体能力检查应尽量非阻塞地在首个页面可交互后继续执行。

## 十、文件上传为什么要和消息发送拆开

图片、语音、附件既是用户体验的一部分，也是生产环境最容易出错的链路之一。

更稳妥的方式是先上传文件，再创建引用文件的消息。文件上传成功后，服务端生成文件标识、文件大小、媒体类型、完整性校验信息、所属企业和上传者等元数据；随后聊天消息只引用 `fileId`，其他客户端按授权地址下载或预览。

这样设计有三个好处。

第一，WebSocket 不会被大文件二进制内容阻塞，新消息和来电事件仍能低延迟到达。

第二，文件下载与预览仍可以按企业、成员和资源关系做权限校验。

第三，真机上传异常时，问题可以被拆开排查：移动网络、HTTPS 证书、Nginx 上传大小、Spring Boot multipart 配置、存储权限、磁盘空间或文件元数据落库。

【插图 11：文件上传与消息引用链路图】

建议图片文字：

客户端上传 -> Nginx 大小/TLS 校验 -> 文件服务 -> 文件存储 + 文件元数据 -> 创建引用 fileId 的消息 -> WebSocket 推送消息元数据 -> 其他端授权预览。

## 十一、生产部署的重点不是 Docker 命令，而是网络与版本边界

本地开发时，可以先初始化数据库，再启动后端、两个 Vue 管理端和 Flutter 客户端。对于本地容器依赖，项目提供 Compose 配置：

```bash
cd deploy/local-docker
docker compose --env-file docker.local.env -f docker-compose.local.yml up -d
```

生产环境中，如果 MySQL 和 Redis 已以宿主机方式稳定运行，没有必要为了形式上的“全容器化”重复部署一套数据库和缓存。应用服务、两个 Vue 前端、Flutter Web、文件预览和音视频服务可以由 Docker Compose 管理，而 Nginx 继续承担 HTTPS、静态资源、API、WebSocket 与媒体信令的反向代理职责。

典型应用更新命令如下：

```bash
cd /opt/shengyu/saas-deploy
docker compose --env-file docker.prod.env \
  -f docker-compose.yml \
  -f docker-compose.prod-host.yml \
  up -d --build server admin-vue3 platform-vue3 im-flutter-web kkfileview
```

需要强调的是，`docker compose up -d` 只是替换服务的动作，不是发布完成的证据。一次完整发布至少应覆盖：

1. 固定代码版本、环境变量、镜像标签。
2. 执行并验证增量 SQL、菜单、按钮权限与默认授权。
3. 检查容器健康状态、Nginx 路由和 TLS 证书。
4. 验证登录、企业切换、联系人、消息、群聊、图片/语音上传。
5. 验证 WSS 重连、Flutter Web 首次打开与刷新缓存。
6. 使用不同网络环境验证语音或视频的呼叫、接听和结束。
7. 记录版本、验收结果与回退位置。

【插图 12：生产发布验收流水线图】

建议图片文字：

构建版本 -> 增量 SQL/权限 -> 替换容器/静态资源 -> 容器与 Nginx 健康检查 -> API/WSS/上传/通话验收 -> 记录版本与回退点。

## 十二、可观测性：让一次问题有共同的关联语言

真实生产问题通常不是出在单一服务。一次“发送消息失败”可能跨越客户端、Nginx、后端、Redis、文件服务和实时通道；一次“接听后无声音”可能涉及客户端权限、业务状态、媒体服务和安全组。

因此，关键日志应围绕关联标识组织，而不是只打印“请求失败”。建议在相关层中使用以下字段：

- `requestId`：一次 API 请求的关联标识。
- `tenantId`：当前企业边界。
- `conversationId`：当前会话。
- `callId`：当前通话。
- `connectionId`：当前实时连接或设备连接。

面向用户的提示应该简洁、可行动，例如“当前通话已结束，请返回会话后重新发起”。面向研发的日志则需要能说明状态变化，例如“期望状态为响铃，实际状态已结束”。

不要把 Token、密码、媒体密钥、完整消息正文、真实账号或文件访问签名写进生产日志。真正专业的可观测性，是既能定位问题，又不扩大数据暴露面。

【插图 13：关联日志图】

建议图片内容：以一个 `callId` 为中心，连接 API 日志、WebSocket 事件、媒体服务状态和客户端错误码。所有值使用示例或脱敏值。

## 十三、从“功能可用”到“可长期演进”，关键是把交付做完整

企业系统的一个功能往往不只是一个接口和一个页面。以新增“应用版本管理”或“企业加入流程”为例，完整交付通常包括：

- 服务端领域逻辑与接口。
- 数据库结构或增量 SQL。
- 平台端或企业端菜单、按钮权限与默认角色配置。
- Vue 和 Flutter 对应页面及路由。
- 实时事件、缓存失效与多端兼容处理。
- 环境变量、部署脚本和生产验收记录。

把这些作为一个整体交付，能避免常见的半上线问题：接口已经发布但前端没有菜单；页面已显示但权限不足；移动端已升级但旧版本无法解析新事件；数据表已增加但生产环境遗漏 SQL。

系统演进也不需要一开始就引入大量基础设施。更有性价比的顺序通常是：先做好租户边界、状态机、日志关联、发布记录和回退路径；再根据真实用户量、消息量、文件量和通话并发，逐步增加缓存优化、异步处理、限流、节点扩容和高可用能力。

## 写在最后

企业协作系统最难的部分，从来不是界面上那条消息气泡，而是让不同端、不同企业、不同网络条件下的状态都能被正确理解。

平台端负责企业边界，企业管理端负责组织与授权，Flutter 客户端负责员工协作体验；Spring Boot 负责业务规则和权威状态；实时通道负责低延迟事件；媒体服务负责音视频传输；MySQL 和 Redis 承担持久化与缓存；Nginx、TLS、WSS、UDP 与 TURN 共同决定生产网络是否真正可用。

当这些边界被清晰地拆开，系统不仅更容易开发，也更容易测试、部署、排障和持续演进。对于做企业管理、协同办公、即时通讯或 Flutter 多端产品的开发者而言，这套思路的价值不在于某一个框架，而在于如何让复杂能力在同一套业务规则下稳定协作。
